# content-service Specification

## Purpose
Отдельный сервис контента на проект: посты, страницы, категории с неограниченной вложенностью (nested sets, перемещение поддеревьев), полиморфное SEO со всеми полями (включая JSON-LD/schema.org), генерация sitemap.xml по флагу индексации и robots.txt на основе данных проекта. Аутентификация и права — через auth-service.

## Requirements

### Requirement: Авторизация через auth-service

Admin-запросы SHALL проверяться по операторскому токену и правам `content.*` через introspection auth-service; public-запросы — по API-ключу проекта. Для проекта с выключенным content-сервисом маршруты SHALL возвращать 404.

#### Scenario: Оператор без права

- WHEN оператор без права публикации пытается опубликовать пост
- THEN возвращается 403

### Requirement: Посты

Admin API SHALL поддерживать CRUD постов проекта: заголовок, slug, контент, локаль, автор, привязка к категориям, статусы `draft → scheduled → published → archived` (недопустимые переходы отклоняются), отложенная публикация по времени. Каждое сохранение SHALL создавать ревизию с возможностью восстановления.

#### Scenario: Отложенная публикация

- WHEN пост в статусе scheduled со временем в будущем
- THEN после наступления времени он публикуется автоматически и появляется в публичном API

#### Scenario: Восстановление из ревизии

- WHEN оператор восстанавливает пост из ревизии
- THEN контент равен снимку, создаётся новая ревизия

### Requirement: Страницы

Admin API SHALL поддерживать создание и редактирование страниц проекта: заголовок, slug (уникален в проекте), контент, локаль, статус публикации, флаг `is_index` (участие в индексации/sitemap).

#### Scenario: Создание страницы

- WHEN оператор создаёт страницу с уникальным slug и публикует её
- THEN страница доступна в публичном API по slug

### Requirement: Категории на nested sets

Категории проекта SHALL храниться деревом неограниченной вложенности (nested sets). Admin API SHALL поддерживать создание, переименование, удаление и **перемещение узла вместе со всем его поддеревом** в любое место дерева; целостность дерева сохраняется при конкурентных операциях. Посты привязываются к категориям; публичное API отдаёт дерево и выборки по категории с потомками.

#### Scenario: Перемещение поддерева

- WHEN оператор перемещает категорию с потомками под другого родителя
- THEN всё поддерево сохраняет внутреннюю структуру, порядок и связи постов, выборки по новому родителю включают перемещённые узлы

#### Scenario: Выборка с потомками

- WHEN публичный запрос просит посты категории с учётом вложенности
- THEN возвращаются посты самой категории и всех её потомков

### Requirement: Полиморфное SEO

SEO-данные SHALL храниться полиморфно и привязываться к любой сущности контента (пост, страница, категория): title, description, keywords, canonical, robots-директивы (noindex/nofollow), Open Graph (og:title, og:description, og:image), Twitter card, произвольный JSON-LD (schema.org). Публичное API SHALL отдавать SEO-блок вместе с сущностью. Валидность JSON-LD (корректный JSON) SHALL проверяться при сохранении.

#### Scenario: SEO для категории

- WHEN оператор задаёт SEO с JSON-LD для категории
- THEN публичный ответ категории содержит все SEO-поля и JSON-LD без изменений

#### Scenario: Невалидный JSON-LD

- WHEN оператор сохраняет синтаксически неверный JSON-LD
- THEN возвращается 422

### Requirement: Генератор sitemap

Сервис SHALL генерировать sitemap.xml проекта из опубликованных сущностей с `is_index = true` (посты, страницы, категории): url, lastmod; сущности с `is_index = false` или noindex SHALL исключаться. Sitemap SHALL отдаваться по публичному маршруту проекта и обновляться при изменениях контента (регенерация асинхронно, не в HTTP-запросе записи).

#### Scenario: Исключение из индекса

- WHEN у опубликованной страницы `is_index` снят
- THEN после регенерации она отсутствует в sitemap.xml

#### Scenario: Публикация попадает в sitemap

- WHEN пост опубликован с `is_index = true`
- THEN он появляется в sitemap.xml с корректным lastmod

### Requirement: Генератор robots.txt

Сервис SHALL генерировать robots.txt проекта на основе его данных и контента: настраиваемые правила Allow/Disallow, ссылка на sitemap, host; закрытые от индексации разделы SHALL попадать в Disallow. Файл SHALL отдаваться по публичному маршруту проекта.

#### Scenario: robots.txt со ссылкой на sitemap

- WHEN сайт запрашивает robots.txt проекта
- THEN ответ содержит актуальные правила проекта и ссылку на его sitemap.xml

### Requirement: Медиа

Admin API SHALL позволять загружать медиа (mime, размер, alt) и использовать их в постах/страницах/SEO (og:image); превью-варианты SHALL генерироваться асинхронно, не в HTTP-запросе.

#### Scenario: Загрузка изображения

- WHEN оператор загружает изображение
- THEN ответ приходит сразу, варианты появляются позже

### Requirement: Публичное API контента

Публичное API по API-ключу проекта SHALL отдавать: посты (списки с фильтрами по категории/локали, курсорная пагинация, одиночные по slug), страницы по slug, дерево категорий — только опубликованное. Ответы SHALL кэшироваться; кэш инвалидируется при публикации/изменении.

#### Scenario: Черновик не виден публично

- WHEN пост в статусе draft
- THEN публичное API его не возвращает

#### Scenario: Публикация сбрасывает кэш

- WHEN пост публикуется
- THEN следующий публичный запрос возвращает его, не дожидаясь TTL

### Requirement: События в аналитику

Сервис SHALL отправлять события жизненного цикла (публикация поста/страницы) в analytics-service асинхронно; недоступность аналитики MUST NOT ломать операции контента.

#### Scenario: Аналитика недоступна

- WHEN analytics-service не отвечает в момент публикации
- THEN публикация проходит успешно, событие доставляется позже (retry с пределом)

### Requirement: Ресёрч, темы и инструкции — разделы content-сервиса

Content-сервис SHALL предоставлять admin API исследований, тем и инструкций проекта. Каждый маршрут MUST быть закрыт отдельным правом: просмотр и запуск исследований, просмотр и управление темами, просмотр и управление инструкциями. Права и пункты навигации новых разделов MUST объявляться в манифесте сервиса, публикуемом в auth-service, — консоль получает состав разделов оттуда.

#### Scenario: Маршрут закрыт правом

- **WHEN** оператор без права запуска исследований обращается к запуску исследования
- **THEN** запрос отклоняется, исследование не создаётся

#### Scenario: Разделы объявлены в манифесте

- **WHEN** content-сервис публикует манифест
- **THEN** манифест содержит права и пункты навигации разделов ресёрча, тем и инструкций

### Requirement: Тяжёлые операции контента выполняются в очереди

Исследование, извлечение тем, генерация поста и сборка проекта SHALL выполняться фоновыми задачами, а не в HTTP-запросе. Задача MUST нести идентификаторы и явный `project_id`, MUST быть идемпотентной при повторной доставке и при окончательном отказе MUST оставлять запись в журнале аудита.

#### Scenario: Долгая операция не держит запрос

- **WHEN** оператор запускает исследование или генерацию поста
- **THEN** HTTP-ответ возвращается сразу, работа выполняется фоновой задачей

#### Scenario: Отказ задачи фиксируется

- **WHEN** фоновая задача исчерпала попытки и завершилась отказом
- **THEN** соответствующая сущность отмечена неуспешной, а отказ попал в журнал аудита

### Requirement: Внешние источники и хранилище знаний настраиваются окружением

Адрес и ключ поисковой службы, адрес хранилища базы знаний и модель векторных представлений SHALL задаваться переменными окружения. Ключи MUST NOT попадать в код, конфигурацию со значениями и журналы. Отсутствие обязательной настройки SHALL приводить к понятной ошибке конфигурации до обращения к сети.

#### Scenario: Смена поисковой службы

- **WHEN** в окружении заданы другой адрес и ключ поисковой службы
- **THEN** исследования выполняются против неё без изменений кода

#### Scenario: Настройка отсутствует

- **WHEN** ключ поисковой службы не задан, а оператор запускает исследование
- **THEN** запуск завершается понятной ошибкой конфигурации, ключ в сообщении не фигурирует
