# shared-platform Specification

## Purpose
Общие контракты, которые делают сервисы платформы согласованными: tenant-контекст, единый формат API (ошибки, пагинация, идемпотентность), service-to-service аутентификация и регистрация манифеста сервиса в control plane.

## Requirements

### Requirement: Tenant-контекст в каждом сервисе

Каждый сервис SHALL резолвить контекст проекта per-request (из сегмента маршрута для admin API, из API-ключа для public API) и MUST NOT хранить его в состоянии, переживающем запрос (Octane-safe). Все таблицы бизнес-данных сервисов MUST иметь `project_id` с автоматическим scope по текущему проекту.

#### Scenario: Изоляция между проектами

- WHEN два последовательных запроса разных проектов обрабатываются одним воркером сервиса
- THEN второй запрос не видит данных и контекста первого

#### Scenario: Фоновая задача

- WHEN джоба выполняется в очереди
- THEN она получает `project_id` явным параметром и восстанавливает контекст сама

### Requirement: Единый формат API

Все сервисы SHALL использовать единый конверт ошибок (код, сообщение, детали по полям, trace id), курсорную пагинацию списков и поддержку ключа идемпотентности для мутирующих public-запросов. Trace id SHALL пробрасываться между сервисами.

#### Scenario: Ошибка валидации в любом сервисе

- WHEN любой сервис отклоняет запрос по валидации
- THEN формат тела 422 одинаков во всех сервисах

#### Scenario: Повтор с тем же Idempotency-Key

- WHEN мутирующий public-запрос повторяется с тем же ключом
- THEN возвращается результат первого выполнения без повторного побочного эффекта

### Requirement: Service-to-service аутентификация

Межсервисные вызовы SHALL аутентифицироваться сервисными credentials; сервисы MUST NOT принимать межсервисные запросы без них. Проверка операторских токенов (guard `admin`), токенов конечных пользователей (guard `web`) и API-ключей проектов другими сервисами SHALL идти через auth-service (introspection) с кэшированием результата и ограниченным TTL; ответ introspection указывает вид субъекта (оператор / пользователь проекта / ключ), project_id и права/scopes.

#### Scenario: Отзыв токена оператора

- WHEN токен отозван в auth-service
- THEN после истечения TTL кэша (минуты, не часы) остальные сервисы отклоняют его с 401

#### Scenario: Межсервисный вызов без credentials

- WHEN сервис получает introspection-запрос без сервисных credentials
- THEN возвращается 401

### Requirement: Манифест сервиса

Каждый сервис SHALL декларировать манифест: key, версию, навигацию админки, права (`<service>.<resource>.<action>`), схемы настроек на проект — и SHALL регистрировать его в auth-service (по команде/на деплое). Права и схемы настроек в auth-service — производные от манифестов, не ручные записи.

#### Scenario: Деплой новой фичи сервиса

- WHEN сервис с новым пунктом навигации и правом регистрирует манифест
- THEN пункт и право появляются в bootstrap-манифесте консоли без изменений в auth-service

### Requirement: Единый запуск стека

Весь стек (gateway, три сервиса, базы данных, Redis, ClickHouse, фронт админки) SHALL подниматься одной командой `docker compose up` из единой конфигурации; сервисы SHALL собираться из одного общего Dockerfile. Каждый сервис SHALL отдавать `/health` после старта.

#### Scenario: Запуск с нуля

- WHEN разработчик выполняет `docker compose up` в свежем клоне
- THEN все сервисы стартуют, `/health` каждого отвечает успешно, фронт админки доступен через gateway

### Requirement: CI/CD-конвейер

CI SHALL на каждое изменение выполнять: тесты всех пакетов и сервисов, сборку кода (composer и npm workspaces), статический анализ (Larastan), сборку фронта админки и проверку актуальности собранного swagger-файла. Провал любого шага SHALL блокировать мёрж.

#### Scenario: Ошибка статического анализа

- WHEN изменение вносит нарушение уровня Larastan
- THEN CI падает и мёрж блокируется

#### Scenario: Фронт не собирается

- WHEN изменение ломает сборку фронта админки
- THEN CI падает

### Requirement: Единая API-документация

Каждый сервис SHALL документировать свои эндпоинты swagger-аннотациями в коде; платформа SHALL предоставлять команду, собирающую документацию всех сервисов в единый swagger-файл. Файл SHALL находиться под версионным контролем, и CI SHALL отклонять изменения API без обновлённой документации. Клиентские типы и хуки панели управления SHALL генерироваться из этого файла.

#### Scenario: Новый эндпоинт без документации

- WHEN сервис добавляет эндпоинт, а собранный swagger-файл не обновлён
- THEN CI-проверка падает

#### Scenario: Сборка общего файла

- WHEN разработчик запускает команду сборки API-документации
- THEN получается один валидный swagger-файл, покрывающий все сервисы

### Requirement: Деньги в минорных единицах

Денежные суммы во всех API и хранилищах SHALL представляться целыми числами в минорных единицах с кодом валюты; float MUST NOT использоваться.

#### Scenario: Сумма в JSON

- WHEN денежное значение отдаётся любым сервисом
- THEN это целое `amount_minor` плюс валюта
