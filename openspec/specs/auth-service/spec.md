# auth-service Specification

## Purpose
Control plane платформы и auth-as-a-service: аутентификация операторов (guard `admin`) и конечных пользователей сайтов проектов (guard `web`, хранение по проекту), роли и права в контексте проекта, tenant-модель (проекты, участники, API-ключи, включение сервисов, настройки, аудит), bootstrap-манифест консоли и introspection для остальных сервисов.

## Requirements

### Requirement: Два guard'а аутентификации

Сервис SHALL разделять два независимых guard'а Sanctum: `admin` — операторы платформы (таблица операторов, глобальная), `web` — конечные пользователи сайтов проектов (хранятся с `project_id`). Токен одного guard'а MUST NOT приниматься маршрутами другого; учётные записи не пересекаются (один email может существовать и как оператор, и как пользователь сайта, и как пользователи разных проектов независимо).

#### Scenario: Токен пользователя сайта на admin API

- WHEN запрос к `/api/admin/v1/*` приходит с токеном guard `web`
- THEN возвращается 401

#### Scenario: Один email в двух проектах

- WHEN пользователь регистрируется с одним email в проекте A и проекте B
- THEN создаются две независимые учётные записи, токены и пароли не пересекаются

### Requirement: Аутентификация операторов

Сервис SHALL аутентифицировать операторов по email/паролю (`/api/admin/v1/auth/*`, guard `admin`): SPA-сессия и Bearer-токены, rate limit на вход, выход с инвалидацией, сброс пароля одноразовым токеном с инвалидацией существующих сессий. `GET /me` SHALL возвращать профиль (id, имя, email, локаль, признак роли `super-admin`); оператор SHALL мочь обновлять имя, локаль, пароль.

#### Scenario: Успешный вход

- WHEN оператор отправляет валидные учётные данные
- THEN выдаётся сессия/токен, последующие admin-запросы авторизованы

#### Scenario: Неверный пароль и rate limit

- WHEN идут многократные неудачные попытки входа
- THEN каждая возвращает ошибку без раскрытия существования аккаунта, после порога — 429

#### Scenario: Сброс пароля

- WHEN оператор подтверждает сброс валидным токеном
- THEN пароль обновлён, старые сессии и токены недействительны, повторное использование токена отклонено

### Requirement: Аутентификация конечных пользователей по проекту

Сервис SHALL предоставлять публичное API `/api/v1/auth/*` (guard `web`), вызываемое сайтом любого проекта по его API-ключу: `register`, `login`, `logout`, `reset-password`, `me`, обновление профиля. Пользователи SHALL храниться с `project_id`; уникальность email — в пределах проекта. Успешные login/register SHALL выдавать Sanctum-токен, привязанный к проекту. Rate limit SHALL действовать на login/register/reset. Токен SHALL действовать только в проекте, где выдан. Запрос сброса пароля SHALL отправлять уведомление с plain-токеном на email пользователя (mail-канал); ответ эндпоинта MUST NOT раскрывать существование email; токен в БД SHALL храниться только хэшем.

#### Scenario: Регистрация с сайта проекта

- WHEN сайт вызывает `/api/v1/auth/register` со своим API-ключом и валидными данными
- THEN создаётся пользователь этого проекта и возвращается Sanctum-токен

#### Scenario: Вход с любого проекта

- WHEN пользователь проекта A логинится через `/api/v1/auth/login` с ключом проекта A
- THEN выдаётся токен; тот же email с ключом проекта B без регистрации в B получает ошибку аутентификации

#### Scenario: Токен чужого проекта

- WHEN запрос приходит с валидным токеном пользователя проекта A, но с API-ключом проекта B
- THEN возвращается 401

#### Scenario: Сброс пароля пользователя сайта

- WHEN пользователь подтверждает сброс валидным одноразовым токеном
- THEN пароль обновлён в рамках его проекта, существующие токены инвалидированы, повторное использование отклонено

#### Scenario: Профиль текущего пользователя

- WHEN сайт вызывает `/api/v1/auth/me` с токеном пользователя
- THEN возвращается профиль пользователя его проекта

#### Scenario: Запрос сброса для существующего email

- WHEN пользователь сайта запрашивает сброс пароля
- THEN на его email уходит уведомление с токеном, ответ — {"sent": true}

#### Scenario: Запрос сброса для неизвестного email

- WHEN запрошен сброс для незарегистрированного email
- THEN уведомление не отправляется, ответ неотличим — {"sent": true}

### Requirement: События аутентификации в историю аналитики

Auth-service SHALL отправлять события жизненного цикла пользователей (регистрация, вход, выход, сброс пароля, блокировка) в analytics-service через `Analytics::push` асинхронно; недоступность аналитики MUST NOT ломать аутентификацию. Аутентификация — стандартная email/password; сторонние OAuth-провайдеры и passkeys — вне объёма этого change.

#### Scenario: Push при регистрации и входе

- WHEN пользователь сайта регистрируется, а затем входит
- THEN в аналитику уходят события register и login с ключом пользователя и project_id

#### Scenario: Аналитика недоступна при входе

- WHEN analytics-service не отвечает
- THEN вход выполняется успешно, событие доставляется позже (retry с пределом)

### Requirement: Управление пользователями проекта из консоли

Admin API SHALL позволять операторам с соответствующими правами (`auth.users.*`) просматривать, блокировать/разблокировывать и удалять пользователей своего проекта; заблокированный пользователь SHALL терять доступ (токены инвалидируются, вход запрещён).

#### Scenario: Блокировка пользователя

- WHEN оператор блокирует пользователя проекта
- THEN его токены недействительны и вход возвращает ошибку

### Requirement: Роли и права на проект

Права SHALL иметь формат `<service>.<resource>.<action>` и происходить из манифестов сервисов. Любая проверка права SHALL выполняться парой (оператор, проект); роль `super-admin` проходит любую проверку в любом проекте. Сервис SHALL предоставлять системные роли и CRUD кастомных ролей на проект, назначение/отзыв ролей участникам. Набор системных ролей SHALL покрывать каждый сервис платформы ролью, дающей доступ только к нему: помимо `owner`, `admin` и `viewer` — `editor` для контента, `analyst` для аналитики, `billing` для оплаты и `licensing` для лицензирования. Системные роли SHALL задаваться шаблонами прав в конфигурации, а не перечислением конкретных прав, и SHALL пересобираться при появлении новых прав. Эффективные права SHALL кэшироваться вне памяти процесса и инвалидироваться при изменении ролей.

#### Scenario: Право в одном проекте, не в другом

- WHEN у оператора роль с правом в проекте A, но не в B
- THEN доступ к ресурсу в A разрешён, в B — запрещён

#### Scenario: Отзыв роли

- WHEN роль отозвана
- THEN со следующего запроса (с учётом TTL кэша introspection в других сервисах) доступ по её правам запрещён

#### Scenario: Роль сервиса открывает только свой сервис

- WHEN участнику назначена роль `billing`
- THEN ему доступны разделы оплаты и закрыты разделы контента, аналитики и управления доступом

#### Scenario: Системная роль защищена от правки

- WHEN оператор пытается изменить состав прав или удалить системную роль
- THEN запрос отклоняется, состав роли остаётся прежним

### Requirement: Синхронизация каталога прав и системных ролей одной командой

Auth-service SHALL предоставлять команду синхронизации доступа, которая приводит каталог прав и системные роли к опубликованным манифестам сервисов. Команда SHALL обрабатывать манифесты всех зарегистрированных сервисов, а не одного; SHALL создавать и обновлять права по их определениям; SHALL создавать недостающие системные роли и пересобирать состав прав существующих во всех проектах платформы. Команда SHALL быть идемпотентной: повторный запуск без изменений в манифестах не меняет состояние. По завершении команда SHALL печатать сводку: сколько прав добавлено и обновлено, сколько ролей пересобрано, какие права не встречаются ни в одном манифесте.

Право, отсутствующее во всех опубликованных манифестах, SHALL по умолчанию только попадать в сводку. Удаление таких прав вместе с их привязками к ролям SHALL выполняться только по явному указанию при запуске.

Синхронизация SHALL сбрасывать кэш эффективных прав и кэш bootstrap консоли и SHALL оповещать остальные сервисы платформы об изменении прав — новый набор SHALL действовать без повторного входа оператора.

#### Scenario: Новое право сервиса расходится по ролям

- **WHEN** сервис опубликовал манифест с новым правом и выполняется синхронизация
- **THEN** право появляется в каталоге, попадает в состав системных ролей, чьи шаблоны ему соответствуют, во всех проектах, и сводка показывает его как добавленное

#### Scenario: Повторный запуск ничего не меняет

- **WHEN** синхронизация выполняется дважды подряд без изменений в манифестах
- **THEN** второй запуск не создаёт и не удаляет ни прав, ни ролей, а сводка показывает нулевые изменения

#### Scenario: Осиротевшее право сохраняется

- **WHEN** право есть в каталоге, но исчезло из всех манифестов, и синхронизация выполняется без указания удалять
- **THEN** право остаётся в каталоге и в ролях, а сводка перечисляет его как осиротевшее

#### Scenario: Явное удаление осиротевших прав

- **WHEN** синхронизация запускается с явным указанием удалять осиротевшие права
- **THEN** такие права удаляются из каталога и из состава всех ролей, включая кастомные, и сводка перечисляет удалённое

#### Scenario: Недостающая системная роль создаётся в существующем проекте

- **WHEN** в шаблоны системных ролей добавлена новая роль и выполняется синхронизация
- **THEN** роль появляется в каждом проекте платформы с правами по своему шаблону

#### Scenario: Изменения видны без перелогина

- **WHEN** синхронизация изменила состав прав роли действующего оператора
- **THEN** следующий запрос bootstrap возвращает новый набор прав без повторного входа

### Requirement: Каталог прав проекта

Auth-service SHALL отдавать admin-эндпоинт каталога прав проекта: по записи на право с его ключом, меткой, группой и сервисом, к которому оно относится. Эндпоинт SHALL требовать право `auth.roles.view`. Каталог SHALL содержать только права сервисов, включённых на проекте: право выключенного сервиса MUST NOT предлагаться к добавлению в роль. Состав прав уже существующей роли SHALL отдаваться полностью, независимо от того, включён ли сервис права.

#### Scenario: Каталог для сборки роли

- **WHEN** оператор с правом `auth.roles.view` запрашивает каталог прав проекта
- **THEN** ответ содержит права с метками и группами, сгруппированные по сервисам платформы

#### Scenario: Права выключенного сервиса не предлагаются

- **WHEN** сервис `pay` выключен на проекте
- **THEN** права `pay.*` отсутствуют в каталоге прав проекта

#### Scenario: Состав роли не урезается

- **WHEN** роль содержит право сервиса, который позже выключили на проекте
- **THEN** это право остаётся в составе роли при её чтении

#### Scenario: Без права доступа

- **WHEN** каталог запрашивает оператор без `auth.roles.view`
- **THEN** доступ запрещён

### Requirement: Проекты и участники

Admin API SHALL поддерживать CRUD проектов (key, name, локали, описание, тематика), архивацию без удаления данных, приглашение/удаление участников. Ключ проекта MAY не передаваться при создании: платформа SHALL вывести его из названия и обеспечить уникальность среди существующих проектов, не требуя действий оператора. Переданный ключ SHALL использоваться как есть, а его занятость SHALL отклоняться ошибкой валидации. Описание и тематика MAY быть пустыми и SHALL изменяться как оператором, так и сборкой проекта по AI. Доступ к проекту имеют только участники (или `super-admin`); не-участнику существование проекта не раскрывается.

#### Scenario: Создание проекта

- WHEN оператор создаёт проект с уникальным key
- THEN проект доступен, у создателя роль owner

#### Scenario: Создание проекта без ключа

- WHEN оператор создаёт проект, передав только название
- THEN проект создаётся с ключом, выведенным из названия, у создателя роль owner

#### Scenario: Выведенный ключ занят

- WHEN название приводит к ключу, который уже занят другим проектом
- THEN платформа создаёт проект с другим уникальным ключом, запрос не отклоняется

#### Scenario: Не-участник

- WHEN оператор без членства запрашивает ресурс проекта
- THEN возвращается 404

#### Scenario: Правка описания и тематики

- WHEN оператор с правом управления проектом изменяет описание и тематику
- THEN новые значения возвращаются при следующем чтении проекта

#### Scenario: Описание в ответе проекта

- WHEN консоль запрашивает текущий проект
- THEN ответ содержит идентификатор, название, описание и тематику проекта

### Requirement: API-ключи проекта

Проект SHALL иметь публичные ключи (только приём аналитических событий) и секретные (server-to-server; хранится хэш, значение показывается один раз) со scopes, отзывом и фиксацией `last_used_at`. Introspection ключей для других сервисов SHALL возвращать project_id, тип и scopes.

#### Scenario: Секрет один раз

- WHEN выпускается секретный ключ
- THEN значение возвращается в ответе однократно и больше нигде не отображается

#### Scenario: Отозванный ключ

- WHEN сервис проверяет отозванный ключ через introspection
- THEN ответ «недействителен», public-запрос получает 401

### Requirement: Включение сервисов на проект

Сервисы платформы SHALL включаться/выключаться на проект. Для выключенного сервиса: его маршруты для проекта возвращают 404 (не 403), навигация не отдаётся в bootstrap, данные не удаляются. Статус включения SHALL быть доступен сервисам через introspection/манифест-API.

#### Scenario: Выключенный сервис

- WHEN консоль или сайт обращается к сервису, выключенному для проекта
- THEN возвращается 404

### Requirement: Настройки сервисов на проект

Значения настроек SHALL валидироваться по схеме из манифеста сервиса; секретные значения SHALL храниться зашифрованными и не возвращаться в открытом виде. Сервис SHALL читать свои настройки проекта через API auth-service (с кэшем).

#### Scenario: Невалидная настройка

- WHEN оператор сохраняет значение не по схеме
- THEN возвращается 422 с указанием поля

### Requirement: Bootstrap консоли

`GET /api/admin/v1/bootstrap` SHALL возвращать полный манифест консоли: профиль, проекты, текущий проект, включённые сервисы с навигацией и схемами настроек (из зарегистрированных манифестов), эффективные права, версию переводов, серверное время. Навигация и права SHALL фильтроваться по включённым сервисам и правам оператора; ответ SHALL кэшироваться и инвалидироваться при регистрации манифестов и смене ролей.

#### Scenario: Консоль одним запросом

- WHEN фронтенд вызывает `/bootstrap`
- THEN ответа достаточно для построения навигации и проверки прав без других запросов

### Requirement: Audit log

Значимые действия (проекты, роли, ключи, включение сервисов, настройки) SHALL записываться в журнал проекта (кто, что, когда, до/после) и читаться через admin API. Остальные сервисы SHALL мочь записывать свои audit-события через service-to-service API.

#### Scenario: Просмотр журнала

- WHEN оператор с правом аудита запрашивает журнал проекта
- THEN возвращается постраничный список с актором и метками времени
