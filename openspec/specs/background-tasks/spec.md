# background-tasks Specification

## Purpose
Определяет единый реестр фоновых задач проекта: платформа знает, что сейчас выполняется, на каком этапе, чем закончилось и почему упало, — чтобы оператор никогда не смотрел в тишину после нажатия кнопки.

## Requirements

### Requirement: Реестр фоновых задач проекта

Платформа SHALL вести реестр фоновых задач проекта. Запись задачи SHALL содержать: вид задачи, проект, оператора-инициатора, состояние (принята, выполняется, завершена, отклонена), текущий этап, время постановки и завершения. Задача SHALL появляться в реестре в момент постановки в очередь, а не в момент начала выполнения: между нажатием кнопки и стартом обработчика оператор уже должен видеть, что задача принята.

#### Scenario: Задача видна сразу после постановки

- **WHEN** оператор запускает фоновую операцию
- **THEN** в реестре сразу появляется запись со состоянием «принята», ещё до начала выполнения

#### Scenario: Ход выполнения обновляется

- **WHEN** обработчик переходит к следующему этапу работы
- **THEN** запись задачи отражает новый этап без ожидания её завершения

#### Scenario: Завершение фиксируется

- **WHEN** обработчик закончил работу
- **THEN** запись переходит в конечное состояние с временем завершения

### Requirement: Причина отказа сохраняется вместе с задачей

Упавшая задача SHALL получать состояние «отклонена» и понятную причину на языке оператора. Причина MUST NOT быть техническим следом исключения: адреса классов, строки стека и SQL наружу не отдаются. Задача, исчерпавшая повторные попытки, SHALL быть отмечена как окончательно упавшая.

#### Scenario: Отказ виден оператору

- **WHEN** фоновая задача завершилась ошибкой
- **THEN** её запись содержит состояние «отклонена» и причину, понятную без чтения логов

#### Scenario: Технические детали не раскрываются

- **WHEN** задача упала на внутренней ошибке
- **THEN** причина описывает суть отказа, а класс исключения, стек и запрос к базе в ответе отсутствуют

#### Scenario: Повторные попытки

- **WHEN** задача повторяется после временной ошибки
- **THEN** её запись остаётся одной и той же, а состояние становится конечным только после исчерпания попыток

### Requirement: Задачи принадлежат проекту

Реестр SHALL быть изолирован по проекту: оператор видит задачи только того проекта, в котором работает. Задача чужого проекта MUST NOT возвращаться ни в списке, ни по прямому запросу.

#### Scenario: Только свой проект

- **WHEN** оператор запрашивает список фоновых задач
- **THEN** возвращаются задачи только текущего проекта

#### Scenario: Чужая задача

- **WHEN** запрашивается задача другого проекта по её идентификатору
- **THEN** платформа отвечает как на несуществующую

### Requirement: Выдача задач для консоли

Admin API SHALL отдавать список фоновых задач проекта: сначала выполняющиеся, затем недавно завершённые. Ответ SHALL позволять консоли показать индикатор без дополнительных запросов: вид задачи, состояние, этап и предмет работы (пост, исследование, медиафайл). Завершённые задачи SHALL оставаться в выдаче ограниченное время, чтобы оператор увидел результат, даже если отошёл от экрана.

#### Scenario: Список для панели

- **WHEN** консоль запрашивает фоновые задачи проекта
- **THEN** в ответе есть выполняющиеся задачи и недавно завершённые, каждая — с видом, состоянием, этапом и предметом

#### Scenario: Пустой список

- **WHEN** в проекте нет ни выполняющихся, ни недавно завершённых задач
- **THEN** возвращается пустой список, а не ошибка

### Requirement: Существующие фоновые операции сообщают ход

Ресёрч, сборка проекта по AI, генерация поста по теме и импорт медиа по ссылке SHALL вести свою запись в реестре. Их собственные состояния MUST оставаться согласованными с записью задачи: исследование, помеченное завершённым, не может иметь задачу в состоянии «выполняется».

#### Scenario: Генерация поста отражается в реестре

- **WHEN** оператор запускает написание поста по теме
- **THEN** в реестре появляется задача, её этапы меняются по ходу работы, а по завершении она ссылается на созданный пост

#### Scenario: Отказ генерации виден как отказ задачи

- **WHEN** генерация поста отклонена по доменному правилу
- **THEN** задача переходит в состояние «отклонена» с той же причиной, что вернула бы платформа

#### Scenario: Состояния не расходятся

- **WHEN** исследование завершилось
- **THEN** его задача в реестре тоже находится в конечном состоянии
