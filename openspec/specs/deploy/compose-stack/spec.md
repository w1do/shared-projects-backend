# deploy/compose-stack Specification

## Purpose
Развёртывание платформы одной командой: самодостаточный compose-стек со всеми настройками в `infra/`, минимумом обязательных переменных, автоматическим бутстрапом и персистентными данными — одинаково для локальной машины и Dokploy (service → compose).

## Requirements

### Requirement: Запуск одной командой из самодостаточного compose

Весь стек — gateway, четыре API-сервиса с воркерами и планировщиком, панель, документация, Postgres, Redis, ClickHouse, MinIO — SHALL подниматься одной командой `docker compose -f infra/compose/compose.yaml up -d` без дополнительных скриптов, флагов и подготовки. Все пути внутри compose-файла (контексты сборки, монтирования конфигураций) SHALL разрешаться относительно самого файла: команда SHALL работать из любого текущего каталога и из систем деплоя, указывающих только путь к файлу. После старта `/health/<service>` каждого сервиса SHALL отвечать успешно, панель SHALL быть доступна через gateway.

#### Scenario: Чистая машина — одна команда

- **WHEN** на чистой машине с Docker выполняется `docker compose -f infra/compose/compose.yaml up -d` на свежем клоне репозитория
- **THEN** стек собирается и стартует, `/health/auth|content|analytics|pay` отвечают успешно, панель открывается через gateway

#### Scenario: Развёртывание в Dokploy

- **WHEN** в Dokploy создаётся сервис типа compose с путём `infra/compose/compose.yaml` и доменом, указывающим на сервис gateway
- **THEN** стек разворачивается штатным деплоем Dokploy, панель и API доступны по домену

### Requirement: Настройки в одном месте с минимумом переменных

Все настройки стека SHALL находиться в `infra/`; отдельные env-файлы на каждый сервис SHALL NOT требоваться для запуска. Каждая переменная приложений (подключения к БД/Redis/ClickHouse/MinIO, межсервисные адреса, лог-уровни) SHALL иметь рабочее значение по умолчанию прямо в compose-файле; переопределения SHALL приниматься из единого корневого env-источника (файл рядом с compose или переменные окружения системы деплоя). Репозиторий SHALL содержать пример корневого env-файла, перечисляющий только переменные, обязательные к переопределению в продакшене (домен, пароли хранилищ, ключи приложений, межсервисный токен, учётные данные первого оператора) с инструкцией генерации значений. Без единого переопределения стек SHALL стартовать в dev-режиме на небезопасных dev-дефолтах.

#### Scenario: Старт вообще без env-файла

- **WHEN** стек запускается без корневого env-файла и переменных окружения
- **THEN** все сервисы стартуют на dev-дефолтах и проходят health-проверки

#### Scenario: Продакшен переопределяет только секреты

- **WHEN** в продакшене заданы только переменные из примера (домен и секреты), прочие не заданы
- **THEN** стек работает: непереопределённые переменные берут значения по умолчанию из compose

### Requirement: Автоматический бутстрап при старте

При старте стека сервисы SHALL самостоятельно приводить себя в рабочее состояние: применять миграции, публиковать свои манифесты в реестре платформы и (auth-сервис) создавать корневого оператора с учётными данными из переменных окружения, если он ещё не существует. Бутстрап SHALL быть идемпотентным: повторные старты MUST NOT создавать дубликаты и MUST NOT перезаписывать изменённые оператором данные. Сразу после первого `up` вход в панель учётными данными из переменных SHALL быть возможен без ручных команд.

#### Scenario: Вход сразу после первого запуска

- **WHEN** стек поднят первый раз на чистых томах и открыта страница входа панели
- **THEN** вход с учётными данными оператора из переменных окружения успешен, разделы панели доступны

#### Scenario: Повторный запуск идемпотентен

- **WHEN** стек перезапускается поверх существующих данных
- **THEN** миграции и публикация манифестов проходят без ошибок, второй оператор не создаётся, изменённый пароль оператора не сбрасывается

### Requirement: Персистентность данных между деплоями

Данные Postgres, ClickHouse, Redis и MinIO SHALL храниться в именованных томах; остановка, повторный запуск и redeploy стека (включая пересборку образов) MUST NOT приводить к потере данных. Удаление данных SHALL требовать явного удаления томов.

#### Scenario: Redeploy сохраняет данные

- **WHEN** стек останавливается, образы пересобираются и стек запускается снова
- **THEN** проекты, контент, лицензии и аналитика на месте, повторный бутстрап данных не затирает

### Requirement: Производственные образы без монтирования исходников

PHP-сервисы и панель SHALL работать из собранных образов, содержащих код и зависимости: запуск базового compose-файла на чистом клоне (без установленных `vendor/` и `node_modules/` на хосте) SHALL работать. Панель SHALL собираться в production-образ на этапе сборки, а не при старте контейнера. Режим разработки — монтирование исходников, локальная публикация портов хранилищ — SHALL выноситься в отдельный override-файл compose и не влиять на производственный запуск.

#### Scenario: Чистый клон без зависимостей на хосте

- **WHEN** базовый compose-файл запускается на клоне без `vendor/` и собранного фронта
- **THEN** образы собираются со всеми зависимостями, стек стартует и проходит health-проверки

#### Scenario: Dev-режим через override

- **WHEN** стек запускается с дополнительным dev-override-файлом
- **THEN** исходники монтируются в контейнеры и правки кода видны без пересборки образов
