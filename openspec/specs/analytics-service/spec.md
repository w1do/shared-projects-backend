# analytics-service Specification

## Purpose
Отдельный сервис аналитики: приём событий от сайтов проектов и других сервисов платформы, буферизованная батч-запись в ClickHouse, агрегаты для дашборда и отчётные API. Аутентификация и права — через auth-service.

## Requirements

### Requirement: Приём событий

`POST /api/v1/collect` SHALL принимать события по публичному ключу проекта (introspection через auth-service, с кэшем) с rate limit и фильтрацией ботов. Другие сервисы платформы SHALL отправлять события по service-to-service каналу. Приём SHALL отвечать 202 сразу: запись идёт в буфер, ClickHouse в HTTP-запросе MUST NOT затрагиваться.

#### Scenario: Событие с сайта

- WHEN сайт отправляет событие с валидным публичным ключом
- THEN ответ 202 возвращается сразу, событие в буфере

#### Scenario: Невалидный или отозванный ключ

- WHEN событие приходит с неверным ключом
- THEN возвращается 401, событие не сохраняется

#### Scenario: Событие от сервиса платформы

- WHEN content-service шлёт событие публикации по service-каналу
- THEN событие принимается с указанным project_id и источником-сервисом

### Requirement: Буферизованная батч-запись

События SHALL накапливаться в устойчивом буфере (переживающем рестарт) и записываться батчами (по размеру или интервалу) фоновым демоном. Одиночные вставки MUST NOT выполняться. Неудачные батчи SHALL попадать в dead-letter с командой повторной отправки.

#### Scenario: ClickHouse недоступен

- WHEN запись батча падает
- THEN события в dead-letter, приём продолжает работать, после восстановления replay дозаписывает без потери

#### Scenario: Повторная запись батча

- WHEN один батч записан дважды
- THEN события дедуплицируются по идентификатору события

### Requirement: Схема события и приватность

Событие SHALL содержать project_id, идентификатор, время, имя, источник, сессию, атрибуцию (UTM), устройство/гео и произвольные свойства; денежные значения — целые минорные единицы. Сырой IP MUST NOT сохраняться — только соль-хэш. Данные SHALL иметь ограниченный срок хранения с автоматической чисткой.

#### Scenario: Событие с IP

- WHEN событие принято
- THEN сохраняется только хэш IP

### Requirement: История пользователя

Сервис SHALL вести полную историю действий пользователя по ключу субъекта: API `Analytics::push($key, $history)` (SDK в shared-пакете + service-to-service endpoint) добавляет запись в хронологию. Ключ SHALL идентифицировать субъект в проекте (пользователь сайта, аноним, оператор). Все значимые события жизненного цикла пользователя (регистрация → push, авторизация → push, сброс пароля, действия на сайте) SHALL попадать в историю; история SHALL быть запрашиваемой целиком в хронологическом порядке через admin API с правами `analytics.*`.

#### Scenario: Регистрация и вход в истории

- WHEN пользователь сайта зарегистрировался, затем авторизовался
- THEN его история содержит обе записи в хронологическом порядке с временными метками

#### Scenario: Просмотр истории из админки

- WHEN оператор с правом запрашивает историю пользователя по ключу
- THEN возвращается вся хронология действий этого субъекта в его проекте

#### Scenario: Push из другого сервиса

- WHEN auth-service или content-service вызывает push по service-каналу
- THEN запись добавляется в историю без блокировки вызывающего запроса (буферизованно)

### Requirement: Агрегаты и отчёты

Дашборд-запросы (обзор, топ страниц, источники, выручка, сессии) SHALL обслуживаться из предагрегированных представлений, не из сырых событий. Admin API SHALL отдавать отчёты в контексте проекта за период, с проверкой прав `analytics.*`.

#### Scenario: Обзор за период

- WHEN оператор с правом запрашивает обзор проекта
- THEN ответ строится по агрегатам и содержит данные только этого проекта

### Requirement: Экспорт отчётов

Экспорт SHALL выполняться асинхронно фоновой задачей с последующей выдачей файла.

#### Scenario: Экспорт большого отчёта

- WHEN оператор запускает экспорт
- THEN запрос завершается сразу, файл доступен позже
