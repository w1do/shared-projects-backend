# Design — fix-known-behavioral-defects

## Context

См. proposal.md — реестр из 12 дефектов, намеренно сохранённых рефакторингом `refactor-ddd-cqrs-packages`. Здесь каждая правка **меняет наблюдаемое поведение**, поэтому режим противоположный рефакторингу: снимки и guard-тесты, зафиксировавшие ошибочное поведение, обновляются — но только осознанно, по одному, с записью «что изменилось и почему» в задаче. Все остальные снимки обязаны остаться нетронутыми: чинится ровно то, что заявлено.

Уточнения по факту чтения кода (влияют на решения):

- `CachedIntrospector::forgetToken()` **мёртв** — ни одного вызывающего в репозитории. Реальная инвалидация introspection-кэша — полный flush через `POST /internal/cache-bust` (DownstreamNotifier). Дефект «ключ не совпадает» — свойство мёртвого кода.
- `PasswordResetTokens::issue()` хэширует `Str::random(64)` и **не возвращает plain** — доставлять сейчас физически нечего: plain-токен теряется в момент выпуска.
- `WebhookEvent` не читается ни одним admin-API — тенант-колонка нужна для инварианта данных и будущих выборок, а не для скоупа запросов.
- Адаптеры `ManualProvider`/`NullProvider` без конструкторов — им per-project конфиг не нужен; механизм конфигурации нужен для будущих реальных провайдеров (Platega и т.п.).
- `provider_accounts` (encrypted credentials, per-project) — готовая таблица под конфиг провайдеров, мёртвая с рождения.

## Goals / Non-Goals

**Goals:** закрыть все 12 пунктов реестра минимально-достаточными правками; каждое изменение поведения защищено обновлённым тестом; инварианты канона (архитектурный гейт, инвентарь `--strict`) остаются в нуле.

**Non-Goals:** outbox/сага для платёжных возвратов (полная транзакционная гарантия внешних вызовов — отдельная работа); доставка reset-токена admin-ветки (по-прежнему «вне MVP»); реальные платёжные провайдеры; точечная инвалидация introspection-кэша (полный flush остаётся штатным механизмом).

## Decisions

1. **Д1 (introspection-кэш): мёртвый `forgetToken()` удаляется**, вместе с его юнит-тестом. Чинить ключ бессмысленно — точечная инвалидация не работала никогда и никем не вызывалась; рабочий механизм один — cache-bust, это фиксируется докблоком `CachedIntrospector`. Ложное чувство безопасности хуже отсутствия метода.
2. **Д2 (refund вне транзакции): порядок сохраняется, добавляется восстановимость.** Переносить HTTP-вызов провайдера внутрь транзакции нельзя (блокировки на время внешнего вызова), outbox — вне масштаба. Фикс: `DB::transaction(..., attempts: 3)` + при исключении записи ПОСЛЕ успешного возврата у провайдера — критический лог с полным контекстом (payment_id, provider, amount) для ручной сверки. Потеря денег молча становится невозможной.
3. **Д3+Д7 (per-project конфиг провайдеров): `provider_accounts` оживает.** `ProviderRegistry::for()` перестаёт игнорировать `$projectId`: резолвит `ProviderAccount` проекта (acrossProjects) и передаёт его `credentials` адаптеру через новый метод порта `PaymentProvider::configure(array $credentials): static` (дефолтная no-op реализация в адаптерах без конфига). Для `'-'` (verify-фаза вебхука) и проектов без аккаунта — поведение прежнее. `ManualProvider`/`NullProvider` конфиг игнорируют — их поведение не меняется.
4. **Д4 (tenant-скоуп WebhookEvent): колонка без глобального скоупа.** 7.9-A: nullable `project_id` + бэкфилл из платежей одной миграцией; `ProcessWebhookEventJob` после резолва платежа проставляет `project_id` события; `RegisterWebhookHandler` заполняет сразу, если `payment_id` из payload резолвится. 7.9-B: **`BelongsToProject` НЕ вешается** — guard 0.8 мутационно доказал, что глобальный скоуп ломает приём вебхуков (у маршрута нет контекста); инвариант CLAUDE.md выполняется наличием и заполнением колонки, а чтения по проекту (когда появятся) обязаны использовать явный `where`. Guard 0.8 обновляется осознанно: приём без контекста работает, `project_id` дозаполняется джобой.
5. **Д5 (ProjectUserController): защита в глубину.** `FindProjectUserQuery` получает явный `where('project_id', $context->required())` — поведение то же (глобальный скоуп уже фильтровал), но корректность перестаёт зависеть от одного невидимого механизма. Guard 0.11(e) остаётся зелёным без правок.
6. **Д6 (team-context): `withTeamThenClear()` удаляется.** Оба потребителя (`CreateProjectHandler`, `ResolveProject`) переводятся на `withTeam()` с восстановлением предыдущего значения: вложенные свопы больше не затирают внешний контекст. В HTTP-запросе предыдущее значение почти всегда `null`, поэтому наблюдаемых изменений в тестах нет — это и проверяется полным прогоном.
7. **Д8 (мёртвый `$order`)** — удалить дословно сохранённый мёртвый код из `StructuredResponseMapper`.
8. **Д9 (доставка reset-токена сайта):** `PasswordResetTokens::issue()` возвращает plain-токен; `ForgotSitePasswordHandler` шлёт `SitePasswordResetNotification` (mail-канал) через `Infrastructure/Notifications/`; `User` получает `Notifiable`. Admin-ветка не меняется (Non-Goal). Тест — `Notification::fake()`; ответ эндпоинта прежний (`{"sent": true}` без раскрытия существования email).
9. **Д10 (очередь media):** `content-worker` слушает `default,media`. Порядок — default первым: перевод/sitemap важнее регенерации превью.
10. **Д11 (валюта): нормализация на записи + бэкфилл + возврат строгой типизации.** `UpsertPlanHandler` сохраняет `strtoupper($currency)` (не валидацией — 201 остаётся 201, меняется только сохранённое значение); миграция приводит `plans.currency`, `payments.currency`, `payment_transactions.currency` к верхнему регистру; после этого возвращаются `Plan::price()`/`Payment::amount()` и Money на четырёх путях чтения, снятых в 7.5. Guard `guard: 7.5` переписывается осознанно: план `usd` теперь хранится и отдаётся как `USD`, и полный цикл, включая возврат, работает.
11. **Д12 (export dates): канон — query-string.** `ReportPeriodRequest` валидирует только query (`validationData() => $this->query()`), тело игнорируется целиком: исчезает абсурд «валидируем то, что не читаем». Наблюдаемое изменение: невалидное **тело** больше не даёт 422 (даёт 202 с дефолтным окном); невалидный **query** — 422 как раньше. Guard 0.9(a) и снимок 422-на-тело обновляются осознанно.

## Risks / Trade-offs

- [Обновление guard-тестов — то самое действие, которое рефакторинг запрещал] → здесь оно легально по построению change, но каждое обновление указывается в задаче явно («обновлён тест X: было …, стало …»); задача без такой записи не считается выполненной. Все остальные снимки — нетронуты (`git status` по `__snapshots__` сверяется в финале).
- [Д10: включение обработки media может разбудить накопленный бэклог джоб] → перед выкаткой воркера — `LLEN queues:media` и осознанный дренаж или очистка.
- [Д11: бэкфилл валюты меняет данные] → миграция обратимая (down невозможен содержательно — фиксируется как necessary one-way с комментарием), выполняется до включения строгой типизации; на pgsql — `UPDATE ... SET currency = UPPER(currency)`.
- [Д12: клиенты, слвшие даты в теле, молча получат дефолтное окно] → таких клиентов нет (панель шлёт query), зафиксировано смоуком; поведение описано в дельта-спеке.

## Migration Plan

Порядок внутри change: Д11-бэкфилл до типизации; Д4-миграция и код заполнения — в одном этапе. Выкатка обычная; воркер media — после проверки бэклога. Откат — git revert; миграции валюты необратимы по данным (регистр исходника не восстановим), что допустимо: нижний регистр и был дефектом.
