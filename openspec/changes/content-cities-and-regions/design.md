# Design: content-cities-and-regions

## Context

Мотивация — в `proposal.md`. Что уже есть: полиморфное SEO (`seo_meta` с `project_id` и morph-связью, тип ограничен перечнем `SeoableType`: post|page|category), каталог SEO проекта и фоновый пересбор SEO по AI (`content-seo-catalog`) с реестром `background_tasks` и прогрессом в консоли, порт `AiOperations` с операцией по произвольной схеме ответа (`runInstruct`), инструкции проекта с закрытым перечнем категорий и предустановленными инструкциями платформы, слаги через `spatie/laravel-sluggable`, курсорная пагинация списков консоли. Тематика проекта хранится в auth и приходит в консоль вместе с проектом.

Чего нет: любой географии. Источник данных — открытый набор [arbaev/russia-cities](https://github.com/arbaev/russia-cities): города России с регионом, федеральным округом, населением и координатами.

## Goals / Non-Goals

**Goals:**

- Справочник регионов и городов, обновляемый одной командой и не требующий ручного ведения.
- Проект работает с обозримым набором городов по умолчанию и разворачивается до полного справочника одним действием.
- SEO города заполняется по тематике проекта пачкой, а не по одному городу руками.

**Non-Goals:**

- Не строим маршрутизацию региональных страниц сайта (поддомены, префиксы путей) — платформа отдаёт данные, адресацию решает сайт проекта.
- Не заводим геокодирование, определение города по IP и расчёт расстояний.
- Не расширяем справочник другими странами: источник один, страна одна; поле страны появится, когда появится второй источник.
- Не переносим города в каталог SEO — у них свой раздел.

## Decisions

### Д1. Справочник общий на платформу, включённость — на проект

`regions` и `cities` — платформенные таблицы без `project_id`: Казань одинакова во всех проектах, дублировать её на каждый проект бессмысленно. Это осознанное исключение из правила «каждая бизнес-таблица имеет `project_id`»: справочные данные бизнес-данными проекта не являются. Проектное состояние живёт в `project_cities` (`project_id`, `city_id`) и подчиняется `BelongsToProject` как обычная таблица.
*Альтернатива* — копия справочника на проект: отвергнута, 1100 строк × число проектов ради данных, которые никогда не расходятся.

### Д2. Данные лежат копией в пакете, `city:sync` умеет обновиться из источника

Копия исходного набора хранится в ресурсах пакета content, и команда по умолчанию читает её: стенд и прод поднимаются без доступа в интернет, а результат прогона воспроизводим. Аргумент источника (путь к файлу или URL) позволяет обновить справочник из репозитория, когда данные там изменятся.
*Альтернатива* — всегда качать по URL: отвергнута, бутстрап стека начинает зависеть от доступности GitHub.

Сопоставление полей источника (название, регион, федеральный округ, население, координаты) фиксируется при реализации по фактической структуре набора.

### Д3. `city:sync` только добавляет и обновляет

Совпадение записи определяется парой «регион + название города». Города и регионы командой не удаляются: у города может быть SEO проекта и включённость, и удаление осиротило бы их молча. Исчезнувшая из источника запись остаётся в справочнике, а команда сообщает о ней в сводке. Команда идемпотентна: повторный прогон без изменений источника ничего не меняет.

### Д4. Стартовый набор — 10 крупнейших, материализуется при первом обращении

Пока проект не открывал раздел, записей включённости у него нет. При первом чтении списка городов проекта платформа создаёт записи для 10 крупнейших по населению — дальше состав меняет только оператор. Действие «включить все» вставляет недостающие строки одним батчем; действие «оставить 10 крупнейших» возвращает набор к стартовому.
*Альтернатива* — считать включёнными первые десять по рангу, пока нет явных записей: отвергнута, «нет записи» тогда означает то включён, то выключен, в зависимости от того, трогал ли оператор соседний город.

### Д5. Город — четвёртый тип полиморфного SEO

`SeoableType` пополняется значением `city`; запись `seo_meta` для города — это `project_id` проекта + morph на общий город. Модель SEO, её валидация и хранение не меняются: расширяется только перечень типов. Один город у двух проектов получает две независимые записи SEO.

### Д6. Каталог SEO городами не пополняется

Каталог `/content/seo` перечисляет посты, страницы и категории — десятки записей. Тысяча городов затопила бы его и сделала бесполезным. Города правятся в своём разделе, где есть отбор по региону и включённости.

### Д7. AI-адаптация — фоновая задача с прогрессом, а не синхронный запрос

Кнопка «AI: адаптировать под проект» ставит фоновую задачу нового вида в общий реестр: оператор сразу видит, что задача принята, на каком она этапе и чем закончилась. Задача обрабатывает включённые города проекта пачками, чтобы прогресс двигался, а не появлялся в конце. Промпт — инструкция новой категории «SEO города» с подстановкой тематики проекта; оператор может переопределить тематику текстом при запуске («доставка бензина», «автопомощь на дорогах»). Для категории заводится предустановленная инструкция платформы — этого требует существующее правило инструкций.

Поведение при отказах повторяет пересбор SEO контента: отказ по городу не затирает его сохранённое SEO и не останавливает задачу, повторный запуск при выполняющейся задаче отклоняется доменной ошибкой.
*Альтернатива* — синхронная генерация по кнопке: отвергнута, тысяча городов не помещается в один HTTP-запрос, а правило платформы требует прогресса для всего, что уходит в очередь.

### Д8. Права и место раздела

В `ContentManifest` добавляются `content.cities.view` и `content.cities.manage` и пункт навигации `content.cities`. Раздел встаёт в группу «Контент» — он открывается и закрывается сервисом `content`, отдельного сервиса «география» не существует. Правка SEO города закрыта `content.cities.manage`: SEO города — часть управления городами, а не отдельная поверхность.

### Д9. Списки — курсорной пагинацией и фильтрами, массовые действия — одним запросом

Список городов проекта отдаётся страницами с поиском по названию, отбором по региону и по включённости — общим механизмом пагинации консоли. «Включить все» и «оставить 10 крупнейших» — по одному запросу с батч-операцией на стороне сервиса; тысяча одиночных запросов из браузера исключена.

## Risks / Trade-offs

- [Справочник без `project_id` нарушает общее правило tenant-изоляции] → правило сохраняется там, где есть проектные данные: включённость и SEO лежат в проектных таблицах, а архитектурный гейт получает явное исключение для справочных таблиц.
- [«Включить все» даёт ~1100 строк включённости на проект, а AI-адаптация — столько же вызовов модели] → включение делается батчем, адаптация — фоновой задачей пачками с прогрессом; стоимость прогона видна оператору до запуска по числу включённых городов.
- [Данные источника меняются, а справочник ничего не удаляет] → расхождения перечисляются в сводке `city:sync`; удаление остаётся ручной операцией, потому что за городом стоят SEO и включённость проектов.
- [Копия данных в пакете устаревает] → команда умеет читать источник по URL, обновление справочника — обычный прогон `city:sync` с аргументом.
- [Тематика проекта пустая, и промпт получается ни о чём] → тематика переопределяется при запуске; при пустой тематике и пустом переопределении задача отклоняется с понятным сообщением, а не генерирует безликий текст.
- [Четвёртый тип SEO расширяет контракт границы `/content/seo/{type}/{id}`] → расширение осознанное и односторонее: прежние значения типа работают как раньше.

## Migration Plan

1. Миграции трёх таблиц и `city:sync` катятся первыми — справочник наполняется до появления раздела.
2. `city:sync` встаёт в бутстрап стека; на существующих стендах команда запускается вручную один раз.
3. Тип SEO `city` и раздел консоли подключаются после наполнения справочника; до этого поведение платформы не меняется.
4. Откат — снятие пункта навигации и прав; таблицы справочника остаются, данные проектов не затрагиваются.
