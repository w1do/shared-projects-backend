# payments/platega-gateway — Delta

## Purpose

Реальный платёжный шлюз Platega: создание транзакции по настройкам проекта, redirect пользователя на платёжную страницу, обработка callback-статусов и фиксация ошибок провайдера.

## ADDED Requirements

### Requirement: Создание платежа через Platega по настройкам проекта
При инициализации платежа через провайдера `platega` система SHALL читать настройки провайдера текущего проекта (credentials, `return_url`, `fail_url`), создавать транзакцию в Platega и сохранять у платежа внешний идентификатор и URL перенаправления. Ответ инициализации (checkout) SHALL содержать `redirect_url` для перенаправления пользователя на платёжную страницу. Сумма SHALL передаваться провайдеру из внутреннего представления в минорных единицах без потери точности.

#### Scenario: Успешная инициализация с redirect
- **WHEN** пользователь оформляет подписку в проекте с активными настройками `platega`
- **THEN** создаётся платёж со ссылкой на внешнюю транзакцию Platega и ответ содержит `redirect_url` платёжной страницы

#### Scenario: Провайдер не настроен
- **WHEN** инициируется платёж через `platega`, а настройки провайдера в проекте отсутствуют или без credentials
- **THEN** система возвращает доменную ошибку «провайдер не настроен», платёж во внешней системе не создаётся

### Requirement: Обработка callback Platega
Система SHALL принимать callback Platega на webhook-эндпоинт, проверять подлинность запроса по секрету из настроек провайдера проекта и применять статусы: `CONFIRMED` → платёж успешен, `CANCELED` → платёж отменён/неуспешен, `CHARGEBACKED` → возврат. Обработка SHALL быть идемпотентной: повторный callback с тем же статусом не меняет состояние повторно.

#### Scenario: Подтверждение оплаты
- **WHEN** Platega присылает callback `CONFIRMED` по существующей транзакции с валидным секретом
- **THEN** платёж переходит в статус «успешен» и активируются связанные с ним эффекты (подписка)

#### Scenario: Невалидная подпись отклоняется
- **WHEN** callback приходит с неверным секретом/подписью
- **THEN** система отклоняет запрос и не меняет статус платежа

#### Scenario: Повторный callback идемпотентен
- **WHEN** Platega повторно присылает callback `CONFIRMED` по уже подтверждённому платежу
- **THEN** состояние платежа и связанные эффекты не применяются повторно

### Requirement: Фиксация ошибок провайдера
При ошибке взаимодействия с Platega (ошибка создания транзакции, отклонение платежа) система SHALL фиксировать сведения об ошибке: статус/код ответа провайдера SHALL сохраняться в `properties` настроек провайдера как последняя ошибка и попадать в аналитический след платежа.

#### Scenario: Ошибка создания транзакции
- **WHEN** Platega отвечает ошибкой на создание транзакции
- **THEN** платёж помечается неуспешным, сведения об ошибке сохранены в `properties` настроек провайдера и в аналитике платежа
