# Design: external-project-snapshot

## Context

См. `proposal.md` — Why. Требования — в `specs/external-project-snapshot/spec.md` и `specs/snapshot-section-rendering/spec.md`.

Что уже есть и на что опирается решение:

- `ServiceManifest` (`packages/cms/contracts`) объявляет `key`, `version`, `permissions[]` (`PermissionDefinition`), `navigation[]` (`NavigationItem{key,label,route,permission,icon,order,children}`), `settings[]`. Манифесты публикуются командой `manifest:publish` в таблицу `service_manifests`.
- `BuildBootstrap` обходит `ServiceManifestRecord`, отбрасывает выключенные для проекта сервисы, фильтрует их навигацию по правам оператора и отдаёт `services[]` + `permissions[]`. Ответ кэшируется на 300 c, версия сбрасывается через `BootstrapCache::bump()`.
- Переключаемые сервисы ограничены жёстким списком `cms-auth.php: services = ['content','analytics','pay']`; `auth` — ядро и в `bootstrap.services[]` не приходит вовсе.
- Видимость разделов консоли считается в `frontends/admin/src/lib/admin/data-source/section-access.ts`: карта «раздел вёрстки → `{service, permission}`», снимок в cookie `console_sections`, guard в `src/proxy.ts`. Разделы без записи в карте скрыты всегда.
- Права — spatie/laravel-permission в teams-режиме, `team_id = project_id`; роли проекта создаются из `system_roles`.
- CI сверяет `src/components`, `src/app` панели с `frontends/source-admin`: новые экраны придётся зеркалить.

## Goals / Non-Goals

**Goals:**

- Внешний проект описывается данными, а не кодом: ни одной строки под конкретный проект.
- Снапшот проходит через тот же путь, что и манифесты, чтобы права, порядок и правило видимости работали без дублирования логики.
- Никакого доверия к содержимому снапшота: адреса, ключи и права приходят от пользователя и проверяются.

**Non-Goals:**

- Конструктор экранов (формы, детальные карточки, графики) — отдельная веха.
- Автоматический вывод колонок из ответа без декларации: делает вёрстку заложником чужого API. Возможен позже как явно включаемый запасной режим, но не как контракт.
- Загрузка снапшота самим внешним проектом по API и синхронизация по расписанию.

## Decisions

### 1. Снапшот приводится к манифесту, а не живёт параллельной сущностью

Активный снапшот транслируется в `ServiceManifest` с ключом `ext:<project-key>` и подставляется в `BuildBootstrap` рядом с манифестами сервисов. Навигация снапшота становится обычным `NavigationItem`, права — `PermissionDefinition`.

Почему так: фильтрация навигации по правам, форма ответа `bootstrap`, кэш и его сброс уже написаны и покрыты тестами. Альтернатива — отдельная ветка `snapshot` в ответе `bootstrap` и своя фильтрация — отвергнута: это второй экземпляр той же логики, который неизбежно разойдётся с первым.

Следствие для фронта: снапшот-разделы приходят тем же путём, что и остальные, и `section-access.ts` расширяется одним правилом — ключ вида `ext:*` берёт требование из самого ответа, а не из статической карты.

### 2. Внешний проект не проходит через `cms-auth.php: services`

Этот список — перечень сервисов, которые платформа поставляет и умеет включать. Внешний проект в него не добавляется: включённость определяется наличием активного снапшота, а не строкой `project_services`. Альтернатива — заводить псевдо-сервис в списке — отвергнута: список конфигурационный, а набор внешних проектов — данные.

### 3. Хранение — отдельная таблица версий, а не колонка в `projects`

`project_snapshots`: `id`, `project_id`, `schema_version`, `payload` (jsonb), `checksum`, `uploaded_by`, `created_at`. Активная версия — ссылка `projects.active_snapshot_id`.

Почему так: снапшот приходит из чужого файла, и «загрузили не то» — штатная ситуация; история версий делает откат операцией на одну строку. Колонка в `projects` этого не даёт. Альтернатива — хранить только активную версию и полагаться на повторную загрузку — отвергнута: исходный файл у оператора может не сохраниться.

### 4. Права снапшота изолируются префиксом

Права из снапшота регистрируются как `ext.<project-key>.<...>` и выдаются ролям проекта. Префикс обязателен и проставляется платформой, а не берётся из файла: иначе снапшот смог бы объявить `auth.settings.manage` и выдать себе доступ к платформенным разделам. Собственные права платформы через снапшот объявить нельзя.

### 5. Внешние вызовы — только через прокси платформы, по описанию, а не по URL из браузера

Панель обращается к платформе, передавая **ключ раздела**, а не адрес: `GET /api/admin/v1/projects/{project}/snapshot/sections/{section}/data?page=…&q=…`. Платформа берёт описание из активного снапшота, собирает адрес сама, проверяет хост по `api.allowed_hosts`, подставляет учётные данные из настроек проекта по `secret_ref` и ограничивает время ожидания.

Почему так: если панель передаёт URL, прокси превращается в открытый ретранслятор запросов — SSRF на внутреннюю сеть. Передавая ключ раздела, платформа выполняет только те запросы, которые описаны в проверенном снапшоте. Альтернатива — прямой запрос из браузера — отвергнута по трём причинам: чужой сервер должен настроить CORS (часто нерешаемо), токен внешнего API оказался бы в браузере, а произвольные адреса из файла — в руках у клиента.

Проверка адресов двухуровневая: при загрузке снапшота (схема, хост в белом списке, не приватный диапазон) и повторно при выполнении запроса, после разрешения DNS — чтобы имя не переехало на внутренний адрес между загрузкой и вызовом.

### 6. Учётные данные внешнего API — в настройках проекта, не в снапшоте

Снапшот содержит только `secret_ref` — имя настройки. Само значение оператор вводит отдельно, оно хранится и маскируется механизмом настроек проекта. Иначе секрет попал бы в файл, в историю версий и в журнал аудита.

### 7. Схема снапшота — версионированная, отклонение целиком

`schema_version` — целое. Платформа поддерживает явный перечень версий; неизвестная отклоняется. Валидация — до сохранения, ошибки собираются списком, частичного применения нет.

Схема первой версии (`schema_version: 1`):

```json
{
  "schema_version": 1,
  "project": { "key": "legacy-shop", "name": "Legacy Shop" },

  "api": {
    "base_url": "https://other.ru/api",
    "auth": { "type": "bearer", "secret_ref": "legacy_shop_token" },
    "allowed_hosts": ["other.ru"],
    "timeout_ms": 5000
  },

  "permissions": [
    { "key": "orders.view", "label": "Просмотр заказов" }
  ],

  "sections": [
    {
      "key": "analyze",
      "name": "Анализировать",
      "icon": "bar-chart",
      "order": 10,
      "permission": "orders.view",
      "view": {
        "type": "table",
        "endpoint": "/orders",
        "rows_path": "data.items",
        "total_path": "data.total",
        "pagination": {
          "type": "page",
          "page_param": "page",
          "size_param": "per_page",
          "size": 25
        },
        "search_param": "q",
        "columns": [
          { "field": "id",            "label": "ID",     "type": "text",     "width": 120 },
          { "field": "customer.name", "label": "Клиент", "type": "text" },
          { "field": "total_minor",   "label": "Сумма",  "type": "money",    "currency_field": "currency" },
          { "field": "status",        "label": "Статус", "type": "badge",
            "map": { "paid": "success", "pending": "warning", "cancelled": "error" } },
          { "field": "created_at",    "label": "Создан", "type": "datetime" }
        ]
      }
    },
    {
      "key": "legacy-admin",
      "name": "Старая админка",
      "icon": "external-link",
      "order": 20,
      "permission": "orders.view",
      "view": { "type": "external", "url": "https://other.ru/admin" }
    }
  ]
}
```

Правила, вытекающие из схемы:

- `permissions[].key` — без префикса; платформа сохраняет их как `ext.<project-key>.<key>`.
- `sections[].key` — уникален в пределах снапшота, маршрут раздела — `/admin/ext/<project-key>/<section-key>`.
- `sections[].permission` — обязателен и MUST ссылаться на объявленное в этом же файле право; раздела без права быть не может.
- `field` — путь через точку; отсутствующее значение даёт пустую ячейку, а не ошибку.
- `type` первой версии: `text`, `number`, `money`, `datetime`, `date`, `bool`, `badge`, `link`.
- `money` — целые минорные единицы, как требует `CLAUDE.md`; валюта из `currency_field` либо фиксированная `currency`.
- `endpoint` — путь относительно `api.base_url`; абсолютные адреса в разделах не допускаются, кроме `view.type: external`.

### 8. Маршрут-каталог во фронте вместо страницы на раздел

Один динамический маршрут `app/admin/ext/[project]/[section]` разбирает описание и рендерит либо `table` штатным `DataGrid`, либо `external`. Новых страниц под конкретные проекты не появляется, зеркалить в `source-admin` нужно один раз.

### 9. Сброс кэша

Загрузка и откат снапшота вызывают `BootstrapCache::bump()` и уведомление downstream, как это уже делает `ToggleServiceHandler`. Отставание состава разделов ограничено TTL кэша `bootstrap` (300 c) — то же поведение, что и у включения сервисов.

## Risks / Trade-offs

- [Прокси — потенциальный SSRF-канал: адреса приходят из файла] → панель передаёт ключ раздела, а не URL; белый список хостов; проверка при загрузке и повторно после разрешения DNS; запрет приватных диапазонов; ограничение времени ожидания.
- [Снапшот может объявить право платформы и расширить себе доступ] → префикс `ext.<project-key>.` проставляется платформой, объявить право вне своего пространства имён нельзя.
- [Внешний API медленный или лежит — раздел «висит»] → таймаут на стороне платформы, ошибка показывается внутри раздела, остальная панель работает.
- [Декларативная схема требует описать каждый экран — порог входа выше, чем «name + endpoint»] → сознательный размен: предсказуемая вёрстка и проверяемость важнее краткости файла; запасной режим автоколонок можно добавить позже, не ломая схему.
- [Чужой ответ может быть большим] → обязательный постраничный просмотр для списков и ограничение размера ответа на стороне прокси.
- [Снапшот и реальное API разъезжаются со временем] → раздел сообщает о несоответствии описанию явно, а не показывает пустую таблицу как успех; история версий позволяет откатиться.

## Migration Plan

Аддитивно: новая таблица `project_snapshots`, ссылка в `projects`, новые эндпоинты и один маршрут во фронте. Проекты без снапшота ведут себя ровно как сейчас — ветка кода не активируется. Откат: снять ссылку на активный снапшот (разделы исчезают, данные версий сохраняются) либо откатить миграцию, если фича не нужна вовсе.

## Open Questions

- Формат постраничного просмотра, отличный от `page/per_page` (курсорный, `offset/limit`), — добавлять ли в первую версию или расширить `pagination.type` позже. На схему и разбиение задач не влияет: поле уже помечено типом.
- Нужен ли предпросмотр снапшота до активации («загрузить, посмотреть, применить») — удобство, решается после первого реального файла.
