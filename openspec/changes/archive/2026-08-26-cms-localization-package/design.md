# Design: cms-localization-package

## Context

См. `proposal.md`; требования — в трёх спецификациях изменения. Зависимость: контракт `ai-operations` из `cms-ai-package` (операция `translate`, форма `key => [locale => value]`).

Что уже есть:

- `Project.locales` (auth) — список локалей проекта; `bootstrap` отдаёт `translations_version` (сейчас — заглушка `Cache::get('bootstrap:version', 1)`).
- Посты: строка-на-локаль + `translation_group` — **модель не трогаем**, это осознанно другой механизм (у поста разные тела по языкам, а не поле-словарь).
- Категории: `name` — строка; `CategoryDTO`, `UpsertCategoryHandler` (слаг из имени через `Str::slug`), nested set со скоупом `project_id`.
- Межсервисный cache-bust: `DownstreamNotifier::cacheBust` (auth → downstream) и `BootstrapCache::bump()` — путь для инвалидации `translations_version` есть.
- Скилл `.ai/skills/sluggable-development`, `.ai/skills/laravel-permission-development` — применяются при реализации.
- Память проекта: конвейер HTTP — FormRequest → DTO → Handler → JsonResource.

## Goals / Non-Goals

**Goals:**

- Один источник переводов на проект: словарь для строк интерфейса, translatable-поля для данных сущностей.
- Совместимость: существующие вызовы API категорий со строковым именем продолжают работать без изменений.
- AI заполняет недостающее, человек остаётся арбитром (пометка автоперевода).

**Non-Goals:**

- Перевод строк админ-вёрстки на ключи словаря и переключатель языка панели — отдельное большое изменение по CI-сверяемой вёрстке.
- Переводимые поля постов; локализация писем; переводы в других сервисах (analytics/pay подключат словарь своими изменениями).
- Редактор переводов как отдельный экран панели.

## Decisions

### 1. Пакет `cms/localization` живёт в content-service

Словарь — контент проекта, его права (`content.translations.*`) и маршруты естественно живут рядом с постами и категориями; там же уже есть `ProjectContext` и `BelongsToProject`. Альтернатива — отдельный микросервис — отвергнута: ни изоляции данных, ни отдельной нагрузки, только сетевые швы.

### 2. Словарь — одна таблица с JSON-значениями

`translations`: `id, project_id, key (unique per project), values jsonb {locale: value}, machine jsonb {locale: bool}, created_at, updated_at`.

JSON вместо строки-на-локаль: запись читается и пишется целиком (форма `key => [locale => value]` — ровно как в постановке и в `TranslateResultDTO`), не нужны join'ы на каждый ключ; словарь проекта — сотни ключей, не миллионы. Пометка автоперевода — параллельный JSON `machine` (`{ru: true}`), а не отдельная таблица: она живёт и умирает вместе со значением.

Валидация локалей — против `Project.locales`: content-service не хранит проектов, поэтому список локалей приходит через существующий механизм (introspection auth-сервиса, как уже делается для прав) и кэшируется; неизвестная локаль — 422.

### 3. Отдача словаря и версия

`GET /content/translations?locale=ru` → плоский `{key: value}` с откатом на локаль по умолчанию (первая в `Project.locales`). Версия переводов — счётчик в кэше content-service, инкремент при любой записи; в `bootstrap` auth-сервис берёт её через существующий cache-bust канал: запись словаря → `DownstreamNotifier`-стиль уведомление auth → `BootstrapCache::bump()`. Панель сравнивает `translations_version` и перезагружает словарь при росте.

Альтернатива — auth ходит в content за версией на каждый bootstrap — отвергнута: лишний межсервисный вызов в горячем пути, кэш bootstrap и так живёт 300 с.

### 4. `Category.name` — spatie/laravel-translatable

`HasTranslations` + `$translatable = ['name']`; миграция: `name` string → jsonb с переносом `{default_locale: старое значение}`. `getRouteKey`/slug не меняются — slug один, генерируется из имени локали по умолчанию (как в постановке: `slug = categories`).

Совместимость API: `UpsertCategoryDTO.name` принимает `string|array`; строка кладётся в локаль по умолчанию (`setTranslation`), массив — целиком (`setTranslations`). `CategoryDTO` отдаёт и `name` (строка запрошенной/дефолтной локали — существующие потребители, включая панель, не меняются), и `name_translations` (полный набор — для формы переводов). Панель в этом изменении продолжает читать `name`.

Альтернатива — перевести категории на строку-на-локаль как посты — отвергнута: категория — один узел дерева с одним slug и одной привязкой постов; дублирование узлов по локалям сломало бы nested set и привязки.

### 5. Автоперевод — Handler + Job поверх `AiOperations::translate`

`TranslateMissingCommand { projectId, subject (dictionary|category), ids?, targetLocales? }` → Job (по канону: ID вместо моделей, явный `project_id`, идемпотентность, `failed()` → журнал). Job собирает недостающее, зовёт `translate` пачкой, пишет значения с `machine=true` в одной транзакции на запись. Уже заполненные локали не трогаются и не отправляются провайдеру (требование «не вызывает провайдера, когда всё переведено» — и экономия токенов).

### 6. Права и манифест

`content.translations.view` / `content.translations.manage` добавляются в `ContentManifest` (permissions; навигацию не добавляем — экрана нет). Роли получают их по существующим маскам (`editor: content.*`).

## Risks / Trade-offs

- [Миграция `name` string→jsonb на живых данных] → миграция переносит значения в один шаг и обратима (down: взять локаль по умолчанию); проверяется тестом на существующем дереве; demo-сидер обновляется на переводимую форму.
- [Расхождение версии переводов между сервисами] → версия — только сигнал устаревания кэша панели; источником словаря остаётся content-service; при потере уведомления версия догонит при следующем bump (тот же компромисс, что у остального bootstrap-кэша).
- [Стоимость автоперевода при больших словарях] → переводится только недостающее, пачками; операция запускается явно, не на каждое сохранение.
- [Панель пока не умеет вводить переводы] → API принимает обе формы; форма панели по локалям — следующее изменение вместе с экраном переводов; ничего в текущей панели не ломается (читает `name`).
- [Ошибочная локаль в jsonb (опечатка ключа локали)] → запись валидируется против `Project.locales` на входе, мусор в данные не попадает.

## Migration Plan

Порядок: миграция словаря (новая таблица — аддитивно) → миграция `categories.name` в jsonb с переносом → код. Откат: down-миграция возвращает строковый столбец из локали по умолчанию; словарь просто перестаёт использоваться. Реализация возможна только после `cms-ai-package` (порт `translate`).

## Open Questions

- Нужен ли импорт/экспорт словаря файлом (JSON) для перевода вне панели — решается после первого реального словаря; на схему хранения не влияет.
