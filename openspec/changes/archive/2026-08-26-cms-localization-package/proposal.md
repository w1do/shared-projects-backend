# Proposal: cms-localization-package

## Why

Панель и контент платформы существуют только на английском, хотя фундамент многоязычности уже заложен: у проекта есть список локалей (`Project.locales`), посты ведутся с `locale`/`translation_group`, а `bootstrap` с первого дня отдаёт `translations_version`. Не хватает самого хранилища переводов и способа их заполнять: ни словаря интерфейсных строк (key → значения по локалям), ни переводимых полей у сущностей (имя категории существует в одном экземпляре), ни инструмента, который переведёт это на языки проекта.

Заполнять переводы руками для каждой локали — нереалистично; пакет `cms/ai` (изменение `cms-ai-package`) даёт операцию `translate`, и локализация строится поверх неё.

## What Changes

- **Новый пакет `packages/cms/localization`** в content-service: словарь переводов проекта — `key → {locale: value}` (форма из постановки: `title = [en => 'Categories', ru => 'Категории']`), CRUD по ключам, отдача словаря целиком для локали.
- **Переводимые поля сущностей** через `spatie/laravel-translatable`: имя категории становится JSON-набором по локалям (`name = {en, ru}`), slug остаётся единым, как в примере постановки. API категорий принимает и отдаёт переводимую форму, оставаясь совместимым со строковой (строка = значение локали по умолчанию).
- **AI-переводы**: операция «перевести недостающее» — для ключей словаря и переводимых полей: берёт значения исходной локали, вызывает `translate` из `cms/ai` и заполняет целевые локали проекта; выполняется в Job, результат помечается как автоперевод до ручного подтверждения.
- **Отдача словаря панели**: эндпоинт словаря по локали + настоящий `translations_version` в `bootstrap` (версия растёт при изменении переводов), чтобы панель могла кэшировать словарь и узнавать об устаревании.
- **Экран управления переводами в панели не входит** — как и замена английских строк вёрстки на ключи словаря: это отдельная большая работа по CI-сверяемой вёрстке (зафиксировано при планировании). Здесь — бекенд, API и данные.
- **Не входит также**: локализация писем/уведомлений, переводимые поля постов (посты уже локализуются строкой-на-язык через `translation_group` — эта модель не меняется), автоматический перевод при каждом сохранении.

## Capabilities

### New Capabilities

- `translation-dictionary`: словарь переводов проекта key → значения по локалям — хранение, изменение, версионирование и отдача панели.
- `translatable-content-fields`: переводимые поля сущностей контента (имя категории) с совместимостью существующего API.
- `ai-translation-fill`: заполнение недостающих локалей словаря и переводимых полей операцией перевода `cms/ai` с пометкой автоперевода.

### Modified Capabilities

нет. `content-categories` (основная спецификация) не меняется на уровне требований: дерево, перемещение и удаление ведут себя по-прежнему; имя категории получает переводимую форму с сохранением совместимости.

## Impact

- Новый пакет `packages/cms/localization` (модель Translation с `project_id`, DTO, Handlers, контроллеры `Api/V1`), маршруты в content-service, права `content.translations.view|manage` в манифесте content.
- `packages/cms/content`: `spatie/laravel-translatable` на `Category.name` (+ миграция строкового столбца в JSON с переносом данных), `CategoryDTO`/Upsert — переводимая форма.
- `packages/cms/auth`: `translations_version` в `bootstrap` начинает отражать реальную версию переводов проекта (через существующий механизм cache-bust между сервисами).
- Панель: слой данных читает словарь и переводимое имя категории; форма категории получает поля по локалям проекта. Правки экранов зеркалятся в `source-admin`.
- Зависимость: **`cms-ai-package` должен быть реализован первым** — операция `translate` используется напрямую.
- E2e-сценарии: словарь через API, переводимое имя категории в панели, автоперевод недостающих локалей (с подменённым провайдером — без сети).
