## Context

Мотивация — в `proposal.md` («Why»). Здесь только то, что определяет подход.

Что есть сейчас:

- **Зеркало.** CI выполняет `diff -r` по `src/components src/app src/styles.css src/theme.css public` между `source-admin` и `admin`. Это симметричная проверка: файл, которого нет в одной стороне, валит билд. Поэтому удалить лишний раздел из консоли сегодня физически нельзя.
- **Два источника данных.** `frontends/admin/src/lib/admin/data-source/config.ts` возвращает `mock` по умолчанию; `shouldUseAdminApi()` ветвит чтения в `queries/*`. Демо-данные лежат рядом с компонентами (`*-mocks.ts`, `utils/`, `config/filters.ts`) и в разделах, у которых сервиса нет вовсе.
- **Разделы.** `section-access.ts` знает 19 разделов, из них 9 подключены к платформе (`SECTION_REQUIREMENTS`). Остальные 10 — товары, варианты, бренды, коллекции, склад, заказы, кампании, акции, поддержка, уведомления — скрыты по требованию «скрыты, но сохранены».
- **Фоновая работа.** Очереди per-service: `content-worker` (`default,media,research`), `auth-worker`, `analytics-worker`, `pay-worker`, плюс `*-scheduler`. У каждой базы свой сервис (`content_service`, `auth_service`, …) — общей БД нет. Ход работы нигде не фиксируется: `ProcessResearchJob` и `BuildProjectJob` меняют статус своей сущности, `GeneratePostJob` не меняет ничего, а его `failed()` пишет в `Log::error` и всё.
- **Версия кода.** `/health` каждого сервиса отдаёт `service`, `status`, `time`. Воркеры при выкате не перезапускаются: образ пересобран, контейнер остался старым — это уже дважды давало «фича в коде есть, но не работает».
- **Линт консоли.** В CI его нет. Локально он красный: тысячи расхождений форматирования в перенесённой вёрстке.

Ограничение, которое держит всю конструкцию: **вёрстка `source-admin` — не должна редактироваться под консоль**. Любое решение, которое требует пройти форматтером по перенесённым файлам, ломает зеркало.

## Goals / Non-Goals

**Goals:**

- В `frontends/admin` остаётся только то, что подключено к платформе; удалённое остаётся доступным в `source-admin` для будущего переноса.
- Одна ветка данных: API платформы.
- Оператор в любой момент видит, что платформа делает в фоне, на каком этапе и чем это кончилось.
- Расхождение версий сервиса и воркера видно без чтения логов.
- Линт консоли зелёный и стоит в CI.

**Non-Goals:**

- Не переносим новые разделы из склада — эта работа только убирает лишнее.
- Не переписываем очередь: остаётся Redis + `queue:work`, без Horizon.
- Не делаем процентный прогресс («47 %») — только именованные этапы.
- Не вводим websockets: обновление — опросом.
- Не трогаем `source-admin`: он остаётся ровно таким, какой есть.

## Decisions

### Решение 1. Зеркало становится односторонним

Проверка меняется с «стороны идентичны» на «пересечение идентично»: для каждого файла, который есть **и** в складе, **и** в консоли, содержимое должно совпадать. Файл, которого нет в консоли, — норма (не перенесли). Файл, которого нет в складе, — норма (собственный код консоли: слой данных, локализация, компоненты под платформу).

Альтернатива — список исключений в CI: пришлось бы вести его руками и он бы устаревал с каждым удалением. Альтернатива «отказаться от сверки» теряет главное свойство: перенесённая вёрстка не должна незаметно расходиться с эталоном.

Оборотная сторона: проверка перестаёт ловить «забыли перенести обратно новый файл, добавленный в консоли». Это осознанный размен — своё в консоли и не обязано попадать в склад.

### Решение 2. Реестр задач живёт в `packages/cms/shared`, таблица — в БД сервиса

Общей БД у сервисов нет, значит единой таблицы задач на платформу быть не может. Реестр — библиотечный код в `shared` (`BackgroundTasks/`: модель, миграция, порт записи хода, ресурс), а таблица создаётся в БД того сервиса, который эти задачи выполняет. Практически сегодня это только `content_service`.

`shared` — библиотека (исключение из four-layer, Decision 9–11), поэтому namespace плоский: `Cms\Shared\BackgroundTasks\*`, без `Domain/Application/Infrastructure`.

Альтернатива — отдельная таблица в каждом модуль-пакете (`research_tasks`, `media_tasks`): консоли пришлось бы опрашивать несколько эндпоинтов и склеивать, а индикатор в панели должен получать всё одним запросом.

Альтернатива — читать `jobs`/`failed_jobs` Laravel: там нет проекта, нет этапа, нет предмета работы, и запись исчезает в момент успеха — оператор ничего не увидит.

### Решение 3. Задача создаётся в контроллере, до диспетчеризации

Между `dispatch()` и стартом обработчика проходит время; если запись заводит сам job, оператор видит тишину ровно в тот момент, ради которого всё делается. Поэтому запись создаёт handler команды, синхронно, и её идентификатор уходит в job. Отсюда состояние `queued` («принята») как отдельное от `running`.

### Решение 4. Ход пишется через порт, а не через модель

Задачам-обработчикам даётся узкий порт `TaskProgress` с двумя-тремя методами (`start`, `stage`, `finish`/`fail`). Job не знает про Eloquent-модель реестра и не может испортить чужие поля. Порт — в `shared`, реализация — там же; пакеты зависят от интерфейса.

### Решение 5. Причина отказа — доменная, не техническая

`failed()` job'а получает `Throwable`. Наружу отдаётся сообщение доменного исключения (`*RuleViolation`), а для всего остального — родовая фраза вида «Не удалось написать пост». Класс исключения, стек и SQL не выходят за пределы лога. Это тот же контракт, что уже действует в HTTP-ответах.

### Решение 6. Обновление — опросом, интервал зависит от наличия работы

Консоль опрашивает список задач: пока есть выполняющиеся — часто (несколько секунд), когда работы нет — редко или не опрашивает вовсе. Websockets потребовали бы брокера и нового канала в gateway ради индикатора в шапке — несоразмерно.

Состояние живёт на платформе, поэтому перезагрузка страницы прогресс не теряет — это следствие решения, а не отдельная механика.

### Решение 7. Завершённые задачи живут ограниченное время

Выдача для консоли содержит выполняющиеся задачи и завершённые за последний короткий срок — чтобы оператор увидел результат, даже если отошёл. Старые записи чистит регулярная задача планировщика. Без этого таблица растёт бесконечно, а индикатор постепенно превращается в архив.

### Решение 8. Удаление разделов — вместе с их данными и маршрутами

Раздел уходит целиком: страница в `src/app`, компоненты в `src/components/pages/<раздел>`, его демо-данные, его запросы в `data-source/queries/*`, его пункт в навигации, его ключи в `section-access.ts` и его тексты в реестре `console.*`. Половинчатое удаление (убрать страницу, оставить запросы) оставит мёртвый код, который не на что проверить.

`components/ui/**` не трогается: это кирпичи, из которых будут собираться следующие разделы.

### Решение 9. Режим `mock` убирается, а не выключается

`getAdminDataSource()`, `shouldUseAdminApi()`, `getAdminMockDelayMs()` и все ветки по ним удаляются. Оставить флаг «по умолчанию api» — значит оставить неисполняемую ветку, которая гниёт: её никто не проверяет, но она мешает читать код.

Побочно: у разделов, которые остаются, часть данных сегодня приходит из демо-набора. Такие места либо получают API платформы, либо (если API нет) блок удаляется вместе с разделом — третьего не остаётся по смыслу этого решения.

### Решение 10. Линт консоли — только по своим файлам

Список файлов для линта строится вычитанием: всё, чего нет в складе. Перенесённая вёрстка не форматируется — иначе рушится зеркало (Решение 1). Это компромисс: единого стиля внутри консоли не будет. Согласованность с эталоном важнее.

### Решение 11. Версия кода — из сборки образа

Версия проставляется в образ на сборке (аргумент сборки → переменная окружения) и читается `/health`. Воркер и планировщик собираются из того же образа, что и сервис, поэтому достаточно отдавать ту же переменную; расхождение видно при сравнении. Вычислять версию из git внутри контейнера нельзя — репозитория там нет.

Перезапуск воркеров при выкате — правило `tools/cms`: команда выката поднимает сервисы и их обработчиков одной операцией, отдельного шага «не забыть воркеры» не остаётся.

## Risks / Trade-offs

- **Удаление разделов заденет то, что используется** (общие утилиты, типы, ключи текстов) → удаляем по одному разделу, после каждого — сборка консоли и тесты; удалённое всегда достаётся из склада или из истории.
- **Одностороннее зеркало перестаёт ловить «забыли синхронизировать обратно»** → компенсируется правилом в `CLAUDE.md`: правка перенесённого файла переносится в склад тем же изменением.
- **Реестр задач добавляет запись в БД на каждую фоновую операцию** → чистка завершённых по расписанию (Решение 7); объём задач в проекте измеряется десятками в день, не тысячами.
- **Опрос создаёт фоновый трафик к API** → опрос идёт только пока есть работа; в покое запросов нет.
- **Разные интервалы опроса и жизни завершённых задач дадут «мигание»** (задача исчезла раньше, чем оператор увидел) → срок жизни завершённой записи заведомо больше интервала опроса.
- **Линт по вычитанию из склада ошибётся, если файл переименовали** → список строится на каждом запуске из фактического состояния обеих сторон, а не хранится.
- **Версия из аргумента сборки не проставится при локальной сборке** → отсутствие версии — валидное значение `unknown`, а не ошибка старта.

## Migration Plan

1. Ослабить проверку зеркала в CI (Решение 1) — иначе следующий шаг не пройдёт.
2. Удалить разделы по одному, каждый — со своими маршрутами, данными и текстами; после каждого прогонять сборку.
3. Убрать `mock` целиком, вместе с оставшимися демо-наборами в подключённых разделах.
4. Добавить реестр задач и порт, подключить существующие фоновые операции.
5. Подключить консоль: индикатор в панели и состояние по месту.
6. Версия кода в `/health`, перезапуск воркеров в выкате.
7. Линт консоли — зелёный локально, затем шаг в CI.

Откат: удаление разделов откатывается переносом из склада (вёрстка там сохранена целиком); реестр задач откатывается снятием миграции — фоновые операции работают и без него, просто молча, как сейчас.
