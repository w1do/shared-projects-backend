## Context

Мотивация — `proposal.md` → «Why». Требования — спеки этого change.

Что есть сейчас и ограничивает решение:

- Четыре Laravel-приложения за gateway; вся логика — в `packages/cms/*` по канону `CLAUDE.md` (four-layer DDD/CQRS, DTO на `spatie/laravel-data`, конвейер FormRequest → DTO → Handler → Resource). Канон проверяется машинно: `packages/cms/shared/tests/ArchitectureGateTest.php` и `./tools/refactor-inventory.sh --strict`.
- `Cms\Ai\Application\Contracts\AiOperations` — единственный порт к модели; реализация `LaravelAiOperations` поверх `laravel/ai` с собственным экземпляром провайдера `cms-ai` (`AiProviderConfig::INSTANCE`), структурный ответ через `StructuredAgent` + `ResponseSchemas`. Операции `suggestCategories()` и `generatePost()` уже есть, но HTTP-потребителей у них нет.
- `Cms\Content` содержит `Post`, `Category` (nested set, `HasTranslations`), полиморфную `SeoMeta`, `Revision`; тенант — трейт `BelongsToProject` + scoped `ProjectContext`. Тегов нет.
- `Cms\Auth\Domain\Models\Project`: `id` (ULID), `key`, `name`, `locales`, `archived_at`. Описания нет.
- Три пакета-донора в рабочем дереве не подключены и не собираются: `packages/cms/instructs` (`Botsync\Instructs`), `packages/cms/research` (`Botsync\Research`), `packages/cms/serp-research` (`PolzaAi\SerpResearch`). Зависят от `botsync/{ai,billing,assistants,support}` и `polzaai/qdrant`, которых в платформе нет; контроллеры вынесены в host-приложение (`App\Http\Controllers\**`), маршруты — `web`/Blade, владение — по `user_id`, слои плоские.
- `laravel/ai` v0.11 умеет эмбеддинги (`Laravel\Ai\Embeddings`, гейтвей `OpenAiCompatible`) — отдельный SDK для векторов не нужен.
- Консоль — Next.js в `frontends/admin`, зеркалируется с `frontends/source-admin` (`components/` и `app/` совпадают побайтово, расходится только `lib/`).

## Goals / Non-Goals

**Goals:**

- Свести доноров к двум пакетам платформы — `cms/research` и `cms/instructs` — по канону, с `project_id` и правами, без следов `botsync/*` и `polzaai/*`.
- Дать базе знаний один порт с обязательным `project_id`, за которым Qdrant — деталь инфраструктуры.
- Сделать сценарии генерации («опиши проект», «собери 10 категорий», «собери 10 тем», «напиши пост») данными инструкции, а не кодом: правило + JSON Schema.
- Замкнуть цепочку ресёрч → база знаний → темы → пост с категориями, тегами и SEO.

**Non-Goals:**

- Тарификация ресёрча и баланс пользователя (донорский `botsync/billing`) — в платформе нет биллинга операций.
- Обучение ассистентов на источниках (`botsync/assistants`) и MCP-сервер донора — отдельные продукты, в платформу не переносятся.
- Голосовой ввод и «улучшение правила» инструкции донора — вне объёма этого change; переносятся при необходимости отдельной задачей.
- Автопубликация сгенерированных постов, планировщик контент-плана, кросс-проектная база знаний.
- Замена существующего конвейера постов: генерация — дополнительный вход, ручное создание поста остаётся как есть.

## Decisions

### 1. Хост — content-service; донорские `research` + `serp-research` сводятся в один пакет `cms/research`

Ресёрч, темы, инструкции и генерация поста живут в `content-service`: там уже `cms/ai`, `cms/content`, категории, SEO и очередь `content-worker`. Генерация поста не пересекает границу сервиса.

Донорское разделение «продуктовая обвязка + пайплайн» существовало ради тарификации и обучения ассистентов; без них два пакета вырождаются в один. `polzaai/serp-research` даёт готовую механику (разбивка промпта на подзапросы, SerpApi, загрузка и очистка страниц, сборка сводного текста) — она переносится в `Infrastructure` нового пакета.

Альтернативы: отдельный `research-service` — отвергнут, генерация поста стала бы межсервисной, а инфраструктура (воркер, манифест, миграции) удвоилась бы; сохранить два пакета — отвергнуто, между ними не осталось границы.

### 2. Доноры переписываются, а не адаптируются точечно

Файлы доноров — источник алгоритмов, не основа. Переносим: `SplitPromptIntoSubQueriesAction`, `SerpApiSearchClient`, `HttpPageContentFetcher` (вместе с его SSRF-защитой), `GenerateArticleAction`, машину этапов `ResearchProgressStage`/`ResearchStatus`, идемпотентность `ProcessResearchJob`, модель снимка `InstructUsage`.

Отбрасываем: `botsync/*` и `polzaai/*` зависимости, `ModuleRegistry`, `AuthUserModel`, `HasInstructs`, web/Blade-маршруты, контроллеры в `App\Http\Controllers\**`, `Policies/` в корне `src/`, MCP-сервер, `InstallCommand`, `example*.png`.

Обязательное при переносе: namespace `Cms\Research` / `Cms\Instructs`, four-layer, провайдер в `Infrastructure/Providers/`, DTO в `Application/DTOs/<Сущность>/` с суффиксом `DTO` и без `rules()`, вся валидация — в `Presentation/Http/Api/V1/Requests/`, ответы — только `JsonResource`, `project_id` во всех таблицах + `BelongsToProject`, конструкторная инъекция вместо `app()`/`config()` в Domain/Application.

Владение меняется с `user_id` на `project_id` — это ломающее изменение для донора, но донор нигде не развёрнут, миграция данных не нужна.

### 3. База знаний — порт в Domain, Qdrant в Infrastructure, одна коллекция с обязательным фильтром по проекту

`Cms\Research\Domain\Contracts\KnowledgeBase` — методы записи точек и поиска; `ProjectId` — обязательный параметр каждого метода, а не неявный контекст. Реализация `QdrantKnowledgeBase` в `Infrastructure/Persistence` ходит в REST API Qdrant через `Illuminate\Support\Facades\Http` — PHP-SDK для Qdrant не берём: нужны четыре вызова (`collections`, `points/upsert`, `points/search`, `points/delete`), зависимость их не окупает.

Хранение — одна коллекция `knowledge` с индексом по payload-полю `project_id` и обязательным фильтром по нему в каждом запросе. Это рекомендованная Qdrant модель мультитенантности; коллекция-на-проект отвергнута: сотни коллекций дороги по памяти и усложняют миграцию схемы.

Payload точки: `project_id`, `topic`, `query`, `content`, `category`, `created_at` (обязательные по спеке) плюс `research_id`, `source_url`, `source_title`. Идентификатор точки — детерминированный UUIDv5 от `project_id + research_id + source_url`: повторная запись прохода перезаписывает ту же точку, дубликат не возникает.

### 4. Эмбеддинги — операция контракта `cms/ai`, а не собственный клиент ресёрча

В `AiOperations` добавляется `embed(EmbedRequestDTO): EmbedResultDTO` и `embeddingDimension(): int`. Реализация — `Laravel\Ai\Embeddings::for()` через тот же экземпляр провайдера `cms-ai`; модель и размерность — из `cms-ai.embedding_model` / `cms-ai.embedding_dimension`. Размерность отдаётся из конфигурации, чтобы создание коллекции не требовало пробного запроса к провайдеру.

Альтернатива — свой HTTP-клиент внутри `cms/research` — отвергнута: в платформе один порт к модели, второй канал к тому же провайдеру размывает правило «смена провайдера = смена окружения».

### 5. Инструкция несёт JSON Schema; схема компилируется в билдер SDK

Инструкция хранит `rule` (текст) и `schema` (JSON Schema в json-колонке). Новая операция `AiOperations::runInstruct(RunInstructRequestDTO): RunInstructResultDTO` принимает правило, схему и входные данные и возвращает разобранный ассоциативный массив.

`StructuredAgent` требует `callable(JsonSchema): array`, а схема приходит данными — нужен компилятор `Cms\Ai\Infrastructure\Ai\JsonSchemaCompiler`, транслирующий поддерживаемое подмножество JSON Schema (`object`, `array`, `string`, `integer`, `number`, `boolean`, `nullable`, `required`, `description`, вложенность) в вызовы билдера. Схема вне подмножества отклоняется до обращения к провайдеру — это и есть проверка «некорректная схема» из спеки инструкций.

Именованные операции `suggestCategories()` и `generatePost()` остаются: они дают типизированный результат для внутренних сценариев. `runInstruct()` — путь для сценариев, форму которых задаёт оператор.

Альтернатива — хранить в инструкции только текст, а форму зашить в код — отвергнута: требование пользователя прямо про «схему JSON, что должен вернуть AI», в инструкции.

### 6. Предустановленные инструкции — сидер платформы, не миграция данных

Пять категорий (`project_description`, `category_tree`, `post_topics`, `post_body`, `post_seo`) получают предустановленные инструкции с `is_system = true` и `project_id = null`. Резолвер `ResolveInstructAction` берёт опубликованную инструкцию проекта нужной категории, иначе — системную. Системные создаются идемпотентным сидером по ключу категории и не редактируются оператором (проверка в Policy и в FormRequest).

### 7. Схема данных ресёрча — нормализованная, донорская `research_results` не переносится

- `researches`: `project_id`, `query`, `offer`, `engine`, `sub_queries_count`, `results_per_sub_query`, `status`, `progress_stage`, `sub_queries` (json), `summary`, `error_message`, `started_at`, `completed_at`, `author_id`.
- `research_sources`: `project_id`, `research_id`, `sub_query`, `position`, `url`, `title`, `content`, `indexed_at`.
- `research_topics`: `project_id`, `research_id`, `title`, `rationale`, `category_id` (nullable), `suggested_category`, `status` (`suggested`/`used`/`rejected`), `post_id` (nullable).

Донорская связка «одна запись `research_results` с json-массивом источников» отвергнута: источники нужны построчно — для показа в консоли, для записи в базу знаний и для отметки `indexed_at`.

Идемпотентность повторного извлечения тем — уникальный индекс `(research_id, title)`; повтор добавляет только новые строки и не трогает `used`/`rejected`.

### 8. Теги — `spatie/laravel-tags` с подменённой моделью тега

Ставим `spatie/laravel-tags` в `content-service`, `Post` получает `HasTags`. Изоляция по проекту — своя модель `Cms\Content\Domain\Models\Tag extends Spatie\Tags\Tag` с `BelongsToProject`, прописанная в `config('tags.taggable.tag_model')`; миграция добавляет `project_id` в `tags` и меняет уникальность на `(project_id, slug, type)`.

Альтернатива — использовать штатное поле `type` как «проект» — отвергнута: `type` уже несёт смысл группы тегов, не даёт внешнего ключа и каскадного удаления вместе с проектом.

### 9. Сборка проекта запускается в content-service, поля проекта пишутся через auth-service

Категории и инструкции живут в content-service, поля проекта — в auth-service. Запуск — `POST api/admin/v1/projects/{project}/buildout` в content-service; фоновая задача выполняет инструкцию, создаёт категории одной транзакцией и обновляет поля проекта одним внутренним вызовом.

Двухфазного коммита между сервисами нет и не будет. Вместо него: каждый шаг атомарен в своём хранилище, порядок фиксирован (категории → проект), повтор идемпотентен — категории сверяются по `slug` в пределах проекта, поля проекта не перезаписываются, если уже заполнены текущей сборкой. Это ровно то, что требует спека `ai-project-buildout` → «Применение результата не оставляет полурезультата».

Понадобится: внутренний эндпоинт обновления проекта в auth-service (`internal.php`) и метод в `Cms\Shared\AuthClient\AuthClient` рядом с `publishManifest()`; аутентификация — существующий `ServiceToken`.

Состояние сборки хранится в content-service (`project_buildouts`: `project_id`, `status`, `topic`, `instruct_usage_id`, `categories_created`, `error_message`, тайминги) — консоль опрашивает его; вторая сборка при непустой выполняющейся отклоняется.

### 10. Долгие операции — Jobs с явным `project_id`, единая очередь `research`

Ресёрч, индексация в базу знаний, извлечение тем, генерация поста и сборка проекта — задачи очереди `research`, обслуживаемой `content-worker` (`--queue=default,media,research`). Отдельный воркер не заводим: очередь разделяет только приоритет, ресёрч не должен занимать всех обработчиков медиа.

Каждая задача несёт идентификаторы и `project_id` (`Cms\Shared\Jobs\ProjectAwareJob`), идемпотентна по состоянию сущности (донорская проверка «завершено/отменено → выход» переносится), `failed()` пишет в аудит.

Запись в базу знаний — отдельная задача после успешного ресёрча: недоступность Qdrant не отменяет результат ресёрча и повторяется по `indexed_at IS NULL`.

### 11. Qdrant — внутренний контейнер без публикации наружу

`qdrant/qdrant` в `infra/compose/compose.yaml` и `compose.dev.yaml`: том `qdrant-data`, сеть `platform`, healthcheck, без `ports:` и без маршрута в gateway. Обращение — только по внутреннему имени `http://qdrant:6333` из content-service и content-worker. Ключи и адреса — переменные окружения (`QDRANT_URL`, `QDRANT_API_KEY`, `SERPAPI_KEY`, `CMS_AI_EMBEDDING_MODEL`).

### 12. Консоль: новые разделы приходят из манифеста, экраны зеркалируются

Права (`content.research.*`, `content.topics.*`, `content.instructs.*`) и пункты навигации объявляются в `ContentManifest`; консоль берёт состав разделов оттуда — правки в `console-navigation` не нужны. Подписи — ключи локализации `nav.content.research`, `nav.content.instructs`, регистрируемые в `ContentLocalizationKeys`.

Экраны добавляются одновременно в `frontends/admin` и `frontends/source-admin`: `components/` и `app/` остаются побайтово идентичными, расходится только `lib/`. Данные — через существующий слой `lib/admin/data-source/platform/content.ts` и очереди запросов `lib/admin/data-source/queries/`.

Прогресс ресёрча и сборки — опрос состояния с интервалом на существующем слое запросов; SSE/websocket не вводим, отдельного канала в gateway для этого не появляется.

## Risks / Trade-offs

- **Компилятор JSON Schema покрывает подмножество** → оператор может написать схему с `oneOf`, `$ref` или рекурсией и получить отказ. Смягчение: отказ явный, с указанием неподдерживаемой конструкции; поддерживаемое подмножество описано в разделе инструкций консоли; предустановленные инструкции остаются в подмножестве.
- **Свободная схема от оператора → непредсказуемый ответ модели** → генерация падает уже после траты запроса. Смягчение: проверка схемы до обращения к провайдеру, одна повторная попытка при несоответствии ответа, отказ без записи в сущности проекта.
- **Ресёрч зависит от внешней поисковой службы и чужих страниц** → отказы, таймауты, мусорный текст. Смягчение: пропуск недоступных источников, ограничение длины извлечённого текста, SSRF-защита переносится из донора без ослабления, полный отказ только когда не осталось ни одного источника.
- **Qdrant — новое звено с состоянием** → потеря тома означает потерю базы знаний. Смягчение: `research_sources` в Postgres остаются источником правды, переиндексация возможна по `indexed_at`; том в compose именованный.
- **Стоимость AI-операций растёт** (эмбеддинги на каждый источник + генерация постов) → неожиданный расход на провайдере. Смягчение: предел одновременных ресёрчей на проект, ограничение числа источников на подзапрос, единый экземпляр провайдера `cms-ai` для учёта.
- **Кросс-сервисная сборка проекта не транзакционна** → окно, где категории созданы, а описание ещё нет. Смягчение: фиксированный порядок, идемпотентный повтор, видимое оператору состояние сборки.
- **Объём change велик** (девять новых возможностей, четыре изменённых, миграции, инфраструктура, консоль) → длинный незакрытый фронт работ. Смягчение: порядок задач в `tasks.md` даёт рабочие срезы — сначала контракт AI и инструкции, затем ресёрч и база знаний, затем темы и посты, консоль последней.
- **`spatie/laravel-tags` с подменённой моделью** → отклонение от документации пакета, обновления пакета нужно проверять. Смягчение: подмена штатная (`tags.taggable.tag_model`), покрывается тестом на изоляцию тегов между проектами.

## Migration Plan

1. Инфраструктура: контейнер `qdrant` и переменные окружения добавляются до кода — сервис поднимается пустым и никем не используется.
2. Миграции добавляют новые таблицы и колонки (`projects.description`, `projects.topic`, `tags.project_id`); существующие таблицы контента не меняются. Откат — `down()` каждой миграции; данных для переноса нет.
3. Донорские пакеты удаляются из рабочего дерева одним шагом вместе с появлением их замен — они не подключены ни к одному приложению, ломать нечего.
4. Коллекция `knowledge` создаётся идемпотентной командой при старте (проверка существования → создание с размерностью из конфигурации); повторный запуск безопасен.
5. Манифест content-сервиса публикуется существующей командой `manifest:publish` — новые права и разделы появляются в консоли после публикации.
6. Откат: снять контейнер `qdrant`, откатить миграции, вернуть прежний манифест. Существующий контент, посты и категории при откате не затрагиваются.
