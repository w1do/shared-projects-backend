# Design: dev-load-seeder

## Context

Мотивация — в `proposal.md`. Текущее состояние: единственный сидер `apps/content-service/database/seeders/DemoContentSeeder.php` наполняет один проект десятком категорий и парой постов; идентификатор проекта он получает из `DEMO_PROJECT_ID`, а сам проект создаёт `tools/smoke.sh` через HTTP. Данные платформы разложены по четырём независимым базам (auth, content, pay — Postgres; analytics — Postgres + ClickHouse), общий ключ между ними — `project_id` (ULID из auth). Категории — nested set (`kalnoy/nestedset`), слаги — `spatie/laravel-sluggable`, медиа — таблица `media_files` поверх диска s3 (MinIO). Аналитические агрегаты `daily_events`, `daily_revenue`, `top_pages` — материализованные представления над таблицей `events`: наполняются самими вставками, отдельный роллап не нужен.

## Goals / Non-Goals

**Goals:**

- Один вход (`./tools/cms seed-load`) и по одному небольшому классу-сеялке на сервис — каждый отвечает только за свои таблицы.
- Прогон по умолчанию — единицы минут на dev-машине; объёмы параметризуются.
- Повторный запуск возвращает стенд в то же состояние без ручной очистки; чужие данные не затрагиваются.

**Non-Goals:**

- Не бенчмарк и не нагрузочное тестирование HTTP: сидер наполняет хранилища, а не измеряет отклик API.
- Не эталон правдоподобия: тексты и суммы синтетические, задача — объём и связность, а не реалистичный контент.
- Не инструмент для production и не часть бутстрапа стека.
- Не замена `DemoContentSeeder` и `tools/smoke.sh` — они остаются как есть.

## Decisions

### Д1. Сеялки — на уровне приложений, запуск через `db:seed`

Классы `LoadSeeder` кладутся в `apps/<service>/database/seeders/` (рядом с `DemoContentSeeder`) и вызываются `php artisan db:seed --class=Database\Seeders\LoadSeeder` внутри контейнера сервиса; оркестрация — подкоманда `tools/cms seed-load`.
*Альтернатива* — artisan-команды в `packages/cms/*/src/Console/`: отвергнута, dev-инструмент уехал бы в production-пакеты и в прод-образы, а пакеты обязаны содержать только доменный код.

### Д2. Владение данными — префикс ключа проекта

Сидер владеет проектами с ключами `load-01 … load-NN`. auth-сеялка — единственный источник истины: она создаёт проекты и печатает их идентификаторы, оркестратор передаёт список остальным сеялкам переменной окружения `LOAD_PROJECT_IDS` (тот же приём, что `DEMO_PROJECT_ID` в `seed-demo`).
*Альтернатива* — таблица-реестр засеянных сущностей: отвергнута, отдельная миграция ради dev-инструмента при том, что префикс ключа однозначно определяет владение.

### Д3. Повторный запуск = удаление своих проектов и посев заново

Каждая сеялка начинает с удаления данных по переданным `project_id`, auth удаляет сами проекты последним шагом. В ClickHouse удаление идёт мутациями `ALTER TABLE ... DELETE WHERE project_id IN (...)` с `mutations_sync=1` по таблице `events` **и по каждому материализованному представлению**: у них собственное хранилище, и чистка источника их не затрагивает. `./tools/cms seed-load 0` выполняет только очистку — это же и способ вернуть стенд к чистому состоянию.
*Альтернатива* — `migrate:fresh` всех сервисов: отвергнута, сносит проект `demo`, ручные данные и требует повторного бутстрапа.

### Д4. Батч-вставки в обход Eloquent, детерминированная генерация

Объёмные сущности (платежи, транзакции, подписки, пользователи сайта, переводы, аудит) вставляются query builder'ом чанками по 2000 строк с ручными `id`/`timestamps`: 400 тыс. платежей через модели заняли бы десятки минут и память. Генератор данных детерминированный (фиксированное зерно на проект), поэтому прогоны воспроизводимы. Модели используются там, где важны доменные инварианты и объёмы малы: дерево категорий (nested set пересчитывает границы), посты со слагами, настройки.
*Альтернатива* — фабрики моделей: отвергнуты для объёмных таблиц по производительности; фабрик в пакетах почти нет, а заводить их ради dev-сидера — лишняя поверхность.

### Д5. Аналитика пишется прямо в ClickHouse

События вставляются батчами (по 50 тыс. строк) через `Connection` пакета analytics, а не через публичный `/api/v1/collect`: 2 млн HTTP-запросов и проход через Redis-буфер несоизмеримы по времени. Поток событий на проект распределён по последнему году и включает как просмотры страниц, так и события платежей с суммами — иначе `daily_revenue` останется пустым, а раздел выручки — нулевым. Агрегаты наполняются самими вставками.

### Д6. Медиа — небольшие сгенерированные файлы напрямую на диск

На проект кладётся несколько десятков маленьких PNG (единицы КБ) в бакет MinIO через диск `s3` с регистрацией строк `media_files`, без конверсий и очередей. Этого достаточно, чтобы увидеть работу S3-диска и раздачу через `/media`, и не превращает прогон в загрузку гигабайтов.

### Д7. Наблюдаемость прогона

Каждая сеялка печатает свои счётчики (сколько чего создано) и время; оркестратор выводит сводную таблицу по сервисам и общее время. Это и есть приёмка требования «прогон соразмерен объёму» — регресс по времени виден сразу.

### Д8. Защита от production

Каждая сеялка первой строкой отказывается работать при `app()->environment('production')`, до любых изменений данных; `tools/cms seed-load` дополнительно не запускается, если у auth-сервиса `APP_ENV=production`. Двойная проверка намеренная: сеялку могут вызвать напрямую через `db:seed`.

### Д9. Разделы, которых ещё нет, пропускаются, а не роняют прогон

Кастомные роли опираются на каталог прав из `access-roles-and-permissions`, города — на справочник и включённость из `content-cities-and-regions`. Сидер проверяет наличие опоры (таблица, эндпоинт, команда) и при её отсутствии пропускает шаг, называя причину в сводке. Иначе dev-инструмент перестанет запускаться на любой ветке, где соседнее изменение ещё не влито, — а его ценность именно в том, что он работает всегда.
*Альтернатива* — жёсткая зависимость и падение прогона: отвергнута, порядок реализации трёх изменений не фиксирован.

## Risks / Trade-offs

- [Объём на диске: ~2 млн строк ClickHouse, ~400 тыс. платежей, медиа в MinIO] → объёмы параметризуются аргументом команды, `seed-load 0` полностью убирает данные; ожидаемый порядок величин фиксируется в документации.
- [Мутации `DELETE` в ClickHouse тяжелее вставок и асинхронны по умолчанию] → выполняются с `mutations_sync=1`, чтобы очистка завершалась до посева; при росте объёмов это самая долгая часть повторного прогона.
- [Детерминированная генерация усыпляет бдительность: одинаковые данные каждый прогон] → зерно выводится из ключа проекта, разные проекты дают разные распределения; при необходимости зерно переопределяется аргументом.
- [Nested set при массовой вставке ломает границы дерева] → категории создаются моделью, размер дерева на проект ограничен несколькими десятками узлов.
- [Память PHP на больших батчах] → генерация через чанки фиксированного размера, никакого накопления полного набора в массиве.
- [Сеялка обращается к внутренним классам пакетов (ClickHouse `Connection`)] → это dev-код уровня приложения, зависящий от своего же сервиса; доменные границы пакетов не нарушаются.

## Migration Plan

1. Сеялки и подкоманда добавляются независимо от остального стека: ничего существующего не меняется, `DemoContentSeeder` и `smoke.sh` продолжают работать.
2. Откат — удаление файлов сидера; данные убираются `./tools/cms seed-load 0` до отката.
3. Документация: раздел про нагруженный стенд и возврат к чистому состоянию.
