## Context

Мотивация — в `proposal.md` («Why»), требования — в `specs/`.

Что уже есть и ограничивает решения:

- Пост хранит контент одним полем `body` (longText). Форма консоли держит `contentBlocks: [{type, content}]` (заголовок/абзац/цитата/изображение), `toPostBody` склеивает их в одну HTML-строку, а `postToArticle` разворачивает её обратно ровно в один блок-абзац: структура теряется на каждом сохранении.
- Ревизии снимают `only(['title','slug','body','locale','status'])`, восстановление заливает `['title','slug','body','locale']` — любое новое поле контента нужно вносить в обе выборки явно.
- Публичный список постов кэшируется целиком телом ответа (`VersionedContentCache`, ключ `content:{project}:v{version}:posts:{md5}`): изменение формы `PostDTO` требует роста версии кэша, иначе сайт получит старый ответ.
- Автор поста уже проставляется платформой: `UpsertPostHandler` пишет `author_id` из introspection оператора. Имена авторов платформа наружу не отдаёт — `postToArticle` ставит `authorName: null`.
- Редактор в консоли — TipTap (HTML). Он остаётся у товаров и брендов; markdown нужен только посту.
- Журнал действий проекта отдаёт `GET /api/admin/v1/projects/{project}/audit` под правом `auth.audit.view`, курсорной страницей: **общего числа записей в ответе нет** — `ApiCursorCollection` кладёт в `meta` только `per_page` и курсоры.
- Верхняя панель: `AdminTopbar` показывает индикатор «сайт онлайн» (ссылка на витрину из localStorage) и кнопку «Новый проект» по `is_super_admin`. Переключателя проектов нет: `project_key` ставится при входе (`applyBootstrap` берёт `current_project`) и при создании проекта. Список проектов оператора уже приходит в `bootstrap.projects`.
- Полноэкранные скелетоны живут в `components/pages/<раздел>/loading/` и подставляются вместо всего раздела по `isPending`. Их 99 файлов на 16 разделов, из которых к платформе подключены шесть.
- `frontends/admin/src/components` побайтово совпадает с `frontends/source-admin/src/components`: правка компонента обязана зеркалиться.
- Панель ставится в контейнере через `bun install --frozen-lockfile` — новая зависимость требует пересчитанного и закоммиченного `bun.lock`.

## Goals / Non-Goals

**Goals:**

- Структура поста переживает сохранение: что оператор разбил на блоки, тем и остаётся.
- Идентификатор блока устойчив и доступен сайту — по нему строится оглавление и переключение частей поста.
- Прежние клиенты публичного API продолжают читать пост, не зная о блоках.
- Оператор всегда видит, в каком проекте работает, и переходит в другой проект тем же путём, каким консоль уже меняет проект.
- Подключённый раздел появляется на экране сразу, а данные подставляются в уже показанный раздел.

**Non-Goals:**

- Имена авторов в списке постов: платформа их наружу не отдаёт, отдельная выдача авторов в эту задачу не входит.
- Богатый редактор блоков (таблицы, вложенные блоки, перетаскивание): блок — это название и markdown-текст.
- Скелетоны демо-разделов вёрстки (товары, заказы, склад и прочие без сервиса платформы) — их не трогаем.
- Права на журнал действий: счётчик опирается на существующее право `auth.audit.view`, ревизия модели прав сюда не входит.
- Перенос HTML прежних постов в markdown: старое тело сохраняется как есть.

## Decisions

### 1. Блоки — JSON-колонка у поста, а не отдельная таблица

Миграция добавляет `posts.blocks` (json, nullable). Блок — `{id, title, markdown}`, порядок задаётся порядком элементов массива.

Почему не таблица `post_blocks`: блоки всегда читаются и пишутся вместе с постом, отдельных выборок «найди блок» у платформы нет. Таблица добавила бы join на каждое чтение поста и колонку порядка, которую всё равно пришлось бы пересчитывать целиком при каждом сохранении.

Почему колонка, а не разбор `body` на лету: идентификатор блока обязан быть устойчивым между сохранениями (спека `content-posts`), а разбор текста даёт новый идентификатор при каждой правке заголовка.

Ревизии: `blocks` вносится в выборки `SnapshotRevisionHandler` и `RestoreRevisionHandler` — иначе восстановление вернуло бы заголовок и текст, но не структуру.

### 2. Идентификатор блока присваивает платформа

Блок без `id` получает ULID при сохранении; переданный `id` сохраняется как есть, если он уникален в пределах поста. Консоль возвращает идентификаторы, которые получила.

Почему не идентификатор из консоли: идентификатор попадает в публичный API и в адреса на сайте — его устойчивость не должна зависеть от того, какой клиент сохранил пост. Дубликат в запросе отклоняется валидацией, а не молча переписывается.

### 3. `body` остаётся и собирается из блоков

При сохранении `body` пересобирается из блоков: `## {title}` и markdown-текст блока через пустую строку; блок без названия даёт только текст. Клиент, который читает пост по прежнему контракту, получает единый текст.

Почему производное поле, а не два независимых: два источника правды разъехались бы при первой же правке через старого клиента. `body` становится проекцией блоков — писать в него отдельно нельзя.

Миграция переносит существующий `body` в один блок `{id: ULID, title: '', markdown: <прежнее тело>}`. Прежние тела — HTML; он остаётся HTML внутри markdown (валидно) и на сайтах рендерится как прежде. Автоматической конвертации HTML → markdown нет намеренно: она необратима и меняет уже опубликованный текст.

### 4. Кэш публичных ответов растёт версией

Форма `PostDTO` меняется, а публичный список лежит в кэше готовым телом. Версия кэша контента поднимается в том же выкате — иначе сайт продолжит получать ответ без блоков до истечения TTL.

### 5. Markdown-редактор — обёртка над `markdown-text-editor`

Пакет `markdown-text-editor@1.5.4` (MIT, зависимости `marked` и `dompurify`) — не React-компонент: он навешивается на нативный `textarea` и не поставляет типов. Поэтому в `components/ui/inputs/` появляется тонкая обёртка: `textarea` под `ref`, инициализация в эффекте, снятие при размонтировании, значение наружу через `onChange`. Типы объявляются локально (`*.d.ts`), потому что пакет их не даёт.

Почему обёртка в `components/ui/`, а не в разделе блогов: правило вёрстки — доменные разделы собираются из общих элементов; редактор блока ничего не знает о постах. Файл зеркалится в `source-admin` наравне с остальными компонентами.

Почему не TipTap, который уже стоит: он даёт HTML, а спека требует markdown как формат хранения; конвертация HTML↔markdown на каждом сохранении — источник расхождений. TipTap остаётся у товаров и брендов без изменений.

Запасной путь, если пакет окажется непригоден в React-обвязке: тот же `textarea` плюс предпросмотр через `marked` — обе зависимости приходят вместе с пакетом.

### 6. Счётчик в кнопке — число последних событий, а не общее

Кнопка показывает `Название (N)`, где N — количество загруженных последних событий журнала, не больше 10; те же события показываются в окне.

Почему не общее число записей: журнал отдаётся курсорной страницей, у которой по построению нет `total`. Добавлять его пришлось бы либо отдельным эндпоинтом счёта, либо ломая контракт `meta` курсорной пагинации, общий для всех списков платформы. Ни то, ни другое задача не оправдывает: оператору нужен признак «в проекте что-то происходило», а не точная величина.

Отсутствие права `auth.audit.view` и недоступность журнала дают кнопку без числа — панель не должна показывать отказ там, где оператор ничего не запрашивал.

### 7. Переключение проекта переиспользует путь смены проекта

Выбор проекта в окне делает то же, что уже делает создание проекта: `setProjectKey` → сброс кэша запросов → перечитывание `bootstrap` выбранного проекта. Список берётся из `bootstrap.projects` — второго запроса за проектами не нужно.

Почему окно, а не выпадающий список в панели: в одном месте собираются три вещи — где я, что здесь происходило и куда перейти; выпадающий список показал бы только третью. Создание проекта переезжает туда же и перестаёт занимать место в панели у операторов, которым оно недоступно.

### 8. Разделы без скелетона: `isPending` доезжает до секции

Полноэкранные `LoadingState` подключённых разделов (категории, блог, ресёрч, инструкции, клиенты, дашборд) удаляются. Раздел рендерится сразу; список получает пустые данные и признак загрузки, чтобы отличать «ещё грузим» от «пусто»: пустое состояние показывается только после прихода данных.

Почему признак, а не пустой список: без него оператор на первом кадре увидел бы «записей нет», а через мгновение — список; это хуже скелетона, а не лучше.

Скелетоны демо-разделов вёрстки остаются: они часть переносимой вёрстки, а не поведения платформы.

### 9. Схема генерации требует блоки

Предустановленная инструкция текста поста (`SystemInstructCatalog`, категория `post_body`) меняет схему ответа: вместо `body` — `blocks` (массив объектов `title` + `markdown`, `minItems: 10`), правило прямо просит разбить материал не менее чем на 10 смысловых частей с собственными заголовками. Разбор в генерации поста читает `blocks`; ответ без них или короче 10 блоков — отказ генерации с понятной причиной, а не пост с одним абзацем.

Пресет «Пост» (`SchemaPresetCatalog`) приводится к тому же составу — иначе падает тест соответствия пресета тому, что платформа разбирает.

## Risks / Trade-offs

- **Пакет редактора без типов и без React-обвязки** → тонкая обёртка с локальными типами и запасной путь (textarea + `marked`), обёртка изолирует пакет от разделов.
- **Новая зависимость панели** → `bun.lock` пересчитывается и коммитится; контейнер ставит зависимости с `--frozen-lockfile` и без обновлённого lock не поднимется.
- **`body` становится производным** → запись в него отдельно от блоков перестаёт иметь смысл; старые клиенты, которые слали `body` в admin API, получают его игнорирование — это фиксируется тестом, а не остаётся сюрпризом.
- **Смешение HTML и markdown в перенесённых постах** → HTML сохраняется как есть внутри блока; конвертация не делается, потому что необратима.
- **Кэш публичных ответов** → версия кэша контента поднимается в том же выкате, иначе сайт получает ответ без блоков.
- **Снятие скелетонов даёт скачок вёрстки** → раздел рендерит свою оболочку с устойчивой высотой, данные подставляются внутрь; проверяется в браузере на медленном ответе.
- **Счётчик почти всегда показывает 10** → это осознанная цена отказа от общего счёта; величина здесь — признак активности, а не метрика.
- **Требование «10 блоков» зависит от модели** → предел проверяется при разборе ответа, отказ объясняется оператору, тема остаётся доступной для повторной попытки.
- **Расхождение `admin` и `source-admin`** → правка любого файла `components/**` попадает в обе копии в рамках той же задачи; проверка — `diff -rq`.

## Migration Plan

1. Миграция контента: `posts.blocks` (json, nullable) + перенос существующего `body` в один блок. Откат снимает колонку; `body` при этом остаётся заполненным, поэтому посты не теряются.
2. Backend: блоки в DTO, валидации, ревизиях и публичном API; `body` начинает собираться из блоков.
3. Поднять версию кэша контента в том же выкате.
4. Инструкция и пресет текста поста переводятся на `blocks`; проекты со своей инструкцией правят её сами — предустановленная обновляется сидером.
5. `./tools/cms api` — пересборка единой спецификации.
6. Панель: `bun install markdown-text-editor`, коммит `bun.lock`, затем обёртка редактора, форма поста, окно проекта и снятие скелетонов; `components/**` зеркалится в `source-admin`.
7. Откат: снять миграцию и вернуть предыдущий образ; посты продолжают читаться по `body`.
