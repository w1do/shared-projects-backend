# licensing/license-keys Specification (delta)

## Purpose

Выпуск, подпись, отзыв и валидация лицензионных ключей self-hosted-поставок: Ed25519-пара проекта, активационный ключ, подписанный лицензионный файл для офлайн-проверки и публичный эндпоинт онлайн-валидации.

## ADDED Requirements

### Requirement: Ключевая пара подписи проекта

Система SHALL поддерживать одну активную Ed25519-пару ключей подписи на проект: пара генерируется автоматически при первой операции, требующей подписи; приватный ключ SHALL храниться только в зашифрованном виде и никогда не возвращаться ни одним API-ответом; публичный ключ SHALL быть доступен через admin-эндпоинт под правом `pay.licensing.manage` для встраивания в поставку.

#### Scenario: Получение публичного ключа проекта

- **WHEN** оператор с правом `pay.licensing.manage` запрашивает публичный ключ проекта
- **THEN** ответ содержит публичный ключ (при отсутствии пары она предварительно генерируется); приватный ключ в ответе отсутствует

#### Scenario: Приватный ключ не покидает хранилище

- **WHEN** любой API-эндпоинт модуля лицензирования возвращает данные
- **THEN** приватный ключ проекта не содержится в ответе ни в открытом, ни в зашифрованном виде

### Requirement: Выпуск лицензии

Система SHALL позволять оператору с правом `pay.licensing.manage` выпустить лицензию для пары организация+план своего проекта с указанием срока действия `expires_at`. При выпуске система SHALL: сгенерировать глобально уникальный активационный ключ формата `LIC-XXXXX-XXXXX-XXXXX-XXXXX-XXXXX` (25 символов Crockford Base32 из криптографического ГСЧ); зафиксировать в подписываемом payload идентификатор лицензии, активационный ключ, название организации, `code` плана, эффективный набор кодов фич (базовые фичи плана + переопределения организации), `issued_at` и `expires_at`; подписать payload приватным ключом проекта. Выпуск для организации или плана другого проекта SHALL быть невозможен.

#### Scenario: Успешный выпуск лицензии

- **WHEN** оператор с правом `pay.licensing.manage` выпускает лицензию для организации и плана текущего проекта со сроком действия в будущем
- **THEN** создаётся лицензия с уникальным активационным ключом, а её payload содержит code плана и эффективные коды фич организации на момент выпуска

#### Scenario: Фичи фиксируются на момент выпуска

- **WHEN** после выпуска лицензии план получает новую базовую фичу
- **THEN** payload ранее выпущенной лицензии не изменяется; новая фича попадает только в лицензии, выпущенные после изменения

#### Scenario: Выпуск без права manage недоступен

- **WHEN** оператор без права `pay.licensing.manage` выпускает лицензию
- **THEN** система возвращает ошибку доступа в стандартном envelope

### Requirement: Лицензионный файл с проверяемой подписью

Система SHALL предоставлять скачивание лицензионного файла под правом `pay.licensing.manage`: base64-конверт JSON `{data, signature}`, где `data` — base64 payload, `signature` — base64 Ed25519-подписи `data`. Подпись SHALL успешно проверяться публичным ключом того же проекта; любое изменение payload SHALL делать подпись невалидной.

#### Scenario: Подпись файла проверяется публичным ключом

- **WHEN** скачанный лицензионный файл декодируется и подпись `data` проверяется публичным ключом проекта
- **THEN** проверка подписи проходит успешно, а payload содержит данные лицензии

#### Scenario: Модифицированный файл не проходит проверку

- **WHEN** в `data` лицензионного файла изменён хотя бы один байт (например, продлён `expires_at`)
- **THEN** проверка подписи публичным ключом завершается неудачей

### Requirement: Статусы и отзыв лицензии

Статус лицензии SHALL вычисляться из фактов: `revoked` при заполненном `revoked_at` (приоритетнее прочих), иначе `expired` при `expires_at` в прошлом, иначе `active`. Оператор с правом `pay.licensing.manage` SHALL иметь возможность отозвать лицензию; отзыв необратим, повторный отзыв SHALL отклоняться доменной ошибкой валидации.

#### Scenario: Отзыв лицензии

- **WHEN** оператор с правом `pay.licensing.manage` отзывает активную лицензию
- **THEN** лицензия получает статус `revoked` и перестаёт проходить онлайн-валидацию

#### Scenario: Истечение срока

- **WHEN** наступает момент позже `expires_at` неотозванной лицензии
- **THEN** лицензия отображается со статусом `expired` без каких-либо действий оператора

#### Scenario: Повторный отзыв отклоняется

- **WHEN** оператор отзывает уже отозванную лицензию
- **THEN** система возвращает доменную ошибку валидации, `revoked_at` не изменяется

### Requirement: Список и просмотр лицензий

Система SHALL предоставлять admin-эндпоинты списка и просмотра лицензий проекта под правом `pay.licensing.view`: организация, план, активационный ключ, `issued_at`, `expires_at`, вычисленный статус. Список SHALL поддерживать пагинацию и фильтрацию по организации и статусу.

#### Scenario: Список лицензий с фильтром по организации

- **WHEN** оператор с правом `pay.licensing.view` запрашивает лицензии конкретной организации
- **THEN** ответ содержит только лицензии этой организации текущего проекта с их вычисленными статусами

### Requirement: Публичная онлайн-валидация ключа

Система SHALL предоставлять публичный эндпоинт валидации без аутентификации, принимающий только активационный ключ. Для лицензии в статусе `active` ответ SHALL содержать: статус, `code` плана, коды фич из payload, `expires_at` — и SHALL NOT содержать персональных данных организации. Для несуществующего, отозванного или истёкшего ключа ответ SHALL быть единым `invalid` без различения причины. Эндпоинт SHALL быть ограничен rate limit'ом. Проект SHALL определяться по самому ключу, без передачи идентификатора проекта клиентом.

#### Scenario: Валидация активного ключа

- **WHEN** поставка отправляет активационный ключ активной лицензии
- **THEN** ответ содержит статус `active`, code плана, коды фич и `expires_at`; анкетных данных организации в ответе нет

#### Scenario: Единый ответ для невалидных ключей

- **WHEN** отправлен несуществующий, отозванный или истёкший ключ
- **THEN** ответ во всех трёх случаях одинаков — `invalid`, без раскрытия причины и без раскрытия существования ключа

#### Scenario: Rate limit на переборе

- **WHEN** с одного источника поступает поток запросов валидации сверх лимита
- **THEN** система отвечает ошибкой ограничения частоты в стандартном envelope
