## Context

Мотивация — в `proposal.md` («Why»), требования — в `specs/`.

Что уже есть и ограничивает решения:

- Категории живут на nested sets (`kalnoy/nestedset`); admin-API умеет только одиночный `DELETE .../categories/{category}`, удаление узла сносит поддерево (`DeleteCategoryHandler`). Дерево консоль получает целиком одним `CategoryTreeQuery` — с `id`, `slug`, `parent_id`.
- В консоли дерево рисует `TreeTable`, у которого нет выбора строк; чекбоксы есть только у `DataGrid`, на который переключается плоский режим.
- `frontends/admin/src/components` и `frontends/source-admin/src/components` **побайтово идентичны** (`diff -rq` пуст). Правка любого компонента обязана зеркалиться в обе стороны; расходиться разрешено только `lib/`.
- Разделы `research` и `instructs` в консоли собраны из голых `div` с утилитарными классами, а не из вёрстки: `sections/*.tsx` вместо `sections/<name>/index.tsx`, самописный `<select>` и `<input type="checkbox">` вместо элементов набора.
- Медиа: `MediaFile` (project_id, disk, path, mime, size, alt, variants), загрузка в S3/MinIO (`UploadMediaHandler`), варианты — джобой на очереди `media`. Права: `content.media.view` / `content.media.manage`.
- У `Post` полей изображений нет вовсе; `ImageUploader` в форме поста кладёт data URL в состояние формы через `FileReader` — до платформы изображение не доходит.
- SerpApi-интеграция живёт в `packages/cms/research` (`SerpSearchClient` → `SerpApiSearchClient`), читает только `organic_results`, движки — `yandex`/`google`.
- Инструкции: схема — колонка `schema` (array) у `Instruct`, состав предустановленных — `SystemInstructCatalog`; консоль правит схему одним `Textarea` с JSON.
- `POST /api/admin/v1/projects` существует, требует `key` и `name`, вешает создателю роль `owner`, включает сервисы по умолчанию и синхронизирует системные роли. Маршрут не закрыт правом. Bootstrap консоли уже отдаёт `is_super_admin`.

## Goals / Non-Goals

**Goals:**

- Массовые операции над категориями выполняются платформой одной транзакцией, а не серией запросов из консоли.
- Изображение поста хранится в MinIO проекта и отдаётся ссылкой платформы — и в admin-, и в публичном API.
- Поиск картинок остаётся в пакете, который владеет интеграцией с поисковой службой; медиа остаются в пакете, который владеет хранилищем.
- Схема инструкции заполняется без набора JSON, при этом ни один вид схемы не теряется при переключении режимов.
- Разделы ресёрча и инструкций перестают отличаться от остальной консоли, без появления новых UI-компонентов.

**Non-Goals:**

- Отдельный раздел «Медиатека» в консоли: медиа остаются доступны из формы поста.
- Автоматическая обложка при генерации поста из темы ресёрча.
- Проверка лицензий найденных изображений и их правообладателей.
- Перевод медиа на `spatie/laravel-medialibrary`: у платформы своё хранилище медиа.
- Галерея изображений поста (решение: обложка и баннер, по одному изображению).
- Ревизия прав `super-admin` и модели ролей: кнопка создания проекта опирается на существующий признак bootstrap.

## Decisions

### 1. Массовое удаление категорий — два аддитивных эндпоинта

`POST .../content/categories/bulk-delete` с телом `{ids: [int]}` и `DELETE .../content/categories` (очистка каталога проекта), оба под `content.categories.manage`. Команды `DeleteCategoriesCommand(list<int> $ids)` и `PurgeCategoriesCommand`, по тонкому handler'у на каждую, обе в одной транзакции.

Почему не серия одиночных `DELETE` из консоли: при nested sets каждый запрос пересчитывает границы дерева, а параллельные удаления родителя и его потомка дают гонку и частично применённое состояние — спека требует «целиком или никак». Один запрос делает это транзакцией и одним пересчётом.

Почему очистка отдельным эндпоинтом, а не `bulk-delete` со всеми id: список id для «удалить все» пришлось бы собирать в консоли и слать килобайтами, а платформа удаляет каталог одним `where project_id` без обхода дерева.

Идемпотентность: несуществующий или чужой id в `ids` молча пропускается (изоляция по проекту уже даёт scope), пустой `ids` — ошибка валидации.

### 2. Полный путь категории считает консоль, а не API

`/родитель/потомок/узел` собирается из уже загруженного дерева по `slug` и `parent_id` (`lib/admin/data-source/category-tree.ts` — там же, где `descendantIds`/`countChildren`, покрыто node-тестами).

Почему не поле `path` в `CategoryResource`: дерево и так приходит целиком, серверный путь стал бы вторым источником правды, который надо поддерживать согласованным при каждом перемещении узла.

### 3. Выбор строк в `TreeTable` — тот же контракт, что у `DataGrid`

`TreeTable` получает `checkbox`, `selectedRowIds`, `onSelectionChange` — свойства с теми же именами и семантикой, что у `DataGrid`, чтобы панель категорий работала с выбором одинаково в обоих режимах. Отметка родителя визуально помечает потомков как «уйдут вместе с ним» (производное состояние, в `selectedRowIds` потомки не добавляются — иначе счётчик выбранного врёт).

Правка `tree-table.tsx` зеркалится в `frontends/source-admin` — иначе ломается инвариант побайтовой идентичности `components/**`.

### 4. Изображения поста — два nullable-столбца со ссылкой на медиа проекта

Миграция в `packages/cms/content/database/migrations` добавляет `cover_media_id` и `banner_media_id` (nullable, FK на `media_files`, `nullOnDelete`). В `UpsertPostDTO` — `int|Optional|null`, валидация в `UpsertPostRequest` проверяет принадлежность медиа текущему проекту. `PostDTO`/`PostResource` отдают вложенный объект медиа (`id`, `url`, `alt`), а не голый id — иначе консоль и публичный клиент делают лишний запрос за каждой обложкой.

Почему не полиморфная привязка «много медиа к посту»: обложка и баннер — фиксированные роли, каждая ровно одна; таблица связей здесь дала бы неопределённость «какое из них обложка».

Удаление медиа не удаляет пост: `nullOnDelete` оставляет пост без изображения.

Уточнено при реализации: `MediaDTO` получает поле `url` рядом с `path`. Ответ загрузки (`POST content/media`) раньше отдавал только путь в хранилище, а адрес хранилища проекта консоли неизвестен — без ссылки платформы форма поста не смогла бы показать только что загруженный файл. Снимки медиа-контракта обновлены осознанно.

### 5. Импорт по ссылке — в content, поиск — в research

`POST .../content/media/import` с телом `{url, alt?}` под `content.media.manage`: скачивает файл и дальше идёт тем же путём, что и загрузка (`MediaFile` + `GenerateMediaVariantsJob`). Скачивание — за портом `Domain/Contracts/RemoteFileFetcher`, реализация в `Infrastructure` на HTTP-клиенте.

`GET .../content/images/search?query=&limit=` остаётся в `packages/cms/research` рядом с остальной SerpApi-интеграцией, под правом `content.media.manage`. Порт `SerpSearchClient` получает вторую операцию `searchImages()`, возвращающую `ImageResultItem` (ссылка на изображение, превью, размеры, источник); движок — новый enum значений `google_images`/`yandex_images`, значение по умолчанию берётся из `cms-research` и согласовано с `RESEARCH_ENGINE`.

Почему граница именно здесь: `cms/content` не должен знать про SerpApi, а `cms/research` — про хранилище медиа. Консоль делает два вызова: поиск → импорт выбранной ссылки. Цена — лишний round-trip, который оператор всё равно тратит на выбор картинки.

Защита импорта: только `http`/`https`, запрет приватных и loopback-адресов после разрешения имени, ограничение числа редиректов, таймаут, предел размера и проверка mime по тем же правилам, что у `UploadMediaRequest`. Неудача не создаёт записи медиа.

### 6. Пресеты схем — рукописный каталог, связанный с разбором тестом

`SchemaPresetCatalog` рядом с `SystemInstructCatalog` (`packages/cms/instructs/src/Infrastructure/Persistence/`), выдача — `GET .../content/instructs/schema-presets` рядом с существующим `instructs/categories`. Пресет: сущность, применимые категории инструкций, список полей (`name`, `type`, `required`, `description`, вложенные `fields`/`items`).

Почему не генерация из PHP-рефлексии DTO: ответ модели и DTO платформы совпадают не полем в поле (в `UpsertPostDTO` есть `locale`, `translation_group`, `is_index`, которых модель не заполняет), а описания полей всё равно пишутся руками. Вместо рефлексии — Pest-тест, который сверяет состав SEO-пресета с полями `UpsertSeoDTO`, а пресета категорий — с формой, которую разбирает `CreateCategoryTreeAction`. Разъезд ловится тестом, а не в проде.

### 7. Визуальный редактор схемы с честным откатом в JSON

Модель поля в консоли — `{name, type, required, description, fields?, items?}`; преобразование «поля ↔ JSON Schema» живёт чистыми функциями в `lib/admin/instructs/schema-fields.ts` рядом с существующим `schema-json.ts` и покрывается node-тестами в обе стороны.

Схема, которую редактор не умеет представить (комбинаторы `oneOf`/`anyOf`, `$ref`, произвольные ключевые слова), **не** упрощается: инструкция открывается сразу в JSON-режиме с пометкой, что схема сложнее редактора. Переключение режимов проходит через одно и то же представление, поэтому не теряет заданных полей.

Почему не полноценный JSON-Schema-билдер: платформа разбирает плоские объекты, массивы объектов и строки — этого набора хватает всем пяти категориям инструкций, а универсальный редактор был бы больше самой задачи.

### 8. Ключ проекта выводит платформа

`CreateProjectDTO::$key` становится `string|Optional`, `CreateProjectRequest` перестаёт требовать `key`. При отсутствии ключа `CreateProjectHandler` получает его из названия: транслитерация в латиницу, kebab-case, обрезка до предела длины; при занятости — числовой суффикс, подбор в той же транзакции, что и создание. Переданный явно ключ работает как прежде, включая ошибку занятости.

Почему не генерировать ключ в консоли: уникальность знает только платформа, а гонка двух операторов с одинаковым названием иначе разрешалась бы ошибкой валидации в лицо оператору.

Кнопка в `AdminTopbar` показывается по `is_super_admin` из bootstrap — признак уже приходит в консоль. Маршрут `POST /projects` остаётся без нового права: сужение доступа к нему — отдельное решение, не входящее в эту задачу.

После успеха консоль ставит `project_key`, сбрасывает кэш запросов и перечитывает bootstrap нового проекта — тем же путём, каким уже происходит смена проекта.

Уточнено при реализации: отдельного переключателя проектов в консоли нет — `project_key` до этой задачи ставился только при входе (`applyBootstrap` берёт `current_project`). Создание проекта переиспользует ровно эту связку (`setProjectKey` → сброс кэша → `getBootstrap`), поэтому переход в новый проект работает, а прежний проект остаётся доступным: он не архивируется, остаётся в `bootstrap.projects`, оператор остаётся его владельцем, и его данные возвращаются при смене `project_key`. Видимый элемент переключения между проектами — отдельная задача, в эту не входит.

### 9. Ресёрч и инструкции — перекладка на вёрстку без новых компонентов

`PageHeader` + `Card variant="form-section"` + `DataGrid`/`Table` + `Badge`/`StatusDot` + `Dialog` + `Skeleton`, структура — `sections/<name>/index.tsx`, как в `categories` и `blogs`. Новые UI-компоненты не создаются: если готового элемента в вёрстке нет, берётся ближайший существующий.

Это следствие правила `admin-console` «вёрстка переносится без изменений»: разделы, собранные мимо набора, — единственное место, где правило нарушено, и они приводятся к остальным.

## Risks / Trade-offs

- **SSRF при импорте по ссылке** → белый список схем, проверка разрешённого адреса на приватные и loopback-диапазоны, ограничение редиректов, таймаут и предел размера; порт скачивания подменяем в тестах.
- **«Удалить все категории» необратимо** → отдельное подтверждение с числом удаляемых категорий, право `content.categories.manage`, запись в audit; действие недоступно на пустом каталоге.
- **Лицензии найденных изображений платформа не проверяет** → в интерфейсе подбора показывается источник каждого изображения; ответственность за использование остаётся на операторе.
- **Квоты и стоимость SerpApi** → жёсткий предел числа результатов, поиск только по явному действию оператора, отсутствие автоподбора при генерации.
- **Расхождение `admin` и `source-admin`** → правка любого файла `components/**` попадает в обе копии в рамках той же задачи; проверка — `diff -rq`.
- **Пресеты разъедутся с тем, что платформа разбирает** → тест соответствия пресетов формам разбора; при добавлении поля в разбор тест падает.
- **`TreeTable` с выбором усложняется** → выбор потомков не хранится, а выводится; счётчик и массовые действия работают только с явно отмеченными узлами.
- **Два столбца медиа у поста вместо гибкой галереи** → если позже понадобятся дополнительные изображения, добавится отдельная связь, столбцы обложки и баннера при этом сохраняются.

## Migration Plan

1. Миграция контента добавляет `cover_media_id` и `banner_media_id` — nullable, существующие посты не меняются; откат снимает столбцы.
2. Новые эндпоинты (`categories/bulk-delete`, `DELETE categories`, `media/import`, `images/search`, `instructs/schema-presets`) аддитивны: старая консоль продолжает работать до выкатки фронта.
3. `CreateProjectRequest` перестаёт требовать `key` — послабление валидации, старые клиенты с `key` работают без изменений.
4. Окружение: `SERPAPI_KEY` уже используется ресёрчем; добавляется движок поиска картинок с безопасным значением по умолчанию — при незаданном ключе подбор отвечает понятной ошибкой, остальные разделы не затрагиваются.
5. После бэкенда — `./tools/cms api` (пересборка единого swagger), затем фронт с обязательным зеркалированием `components/**` в `source-admin`.
6. Откат: снять миграцию и вернуть предыдущий образ; неиспользуемые эндпоинты безопасны сами по себе.
