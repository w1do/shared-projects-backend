# Design: access-roles-and-permissions

## Context

Мотивация — в `proposal.md`. Что уже есть в коде: каждый пакет объявляет `ServiceManifest` со списком `PermissionDefinition` (ключ, метка, группа) и публикует его в auth командой `manifest:publish` — запись ложится в таблицу `service_manifests`. `PermissionCatalog` делает upsert прав из манифеста в таблицу `permissions` (guard `admin`, поля `label` и `group`), `PermissionSyncer` после этого ставит `SyncSystemRolesJob`, а `SystemRoleSyncer` раскрывает wildcard-шаблоны из `cms-auth.system_roles` в роли конкретного проекта (`project_id` = team-скоуп spatie). Кастомные роли проекта уже имеют CRUD: `RoleController` + `RolePolicy`, которая запрещает править и удалять системные роли. Изменение состава прав роли дёргает `BootstrapCache::bump()` и `DownstreamNotifier::cacheBust()` — консоль и другие сервисы видят новый набор без перелогина.

Чего нет: команды, приводящей каталог и роли к манифестам целиком; выдачи каталога прав наружу; экрана ролей в консоли.

## Goals / Non-Goals

**Goals:**

- Одна идемпотентная команда, после которой каталог прав и системные роли всех проектов соответствуют опубликованным манифестам.
- Оператор собирает роль в интерфейсе из списка прав, а не угадывает ключи.
- Каждый сервис платформы покрыт системной ролью, дающей доступ только к нему.

**Non-Goals:**

- Не меняем формат прав `<service>.<resource>.<action>` и не заводим новые права под управление доступом: экран закрывается существующими `auth.roles.view` / `auth.roles.manage`.
- Не переносим источник прав из манифестов в интерфейс: права по-прежнему объявляются кодом сервиса, руками их не заводят.
- Не трогаем механику `Gate::before` для `super-admin` и teams-режим spatie.
- Не переписываем назначение ролей участникам на бэкенде — меняется только способ выбора роли в консоли.

## Decisions

### Д1. `permissions:sync` — команда auth-сервиса поверх таблицы манифестов

Команда живёт в `packages/cms/auth/src/Console/`, читает все записи `service_manifests`, прогоняет каждую через `PermissionCatalog`, затем раскрывает системные роли по всем проектам. Источник истины — опубликованные манифесты, а не код чужих пакетов: auth не может импортировать `PayManifest`, а в проде сервисы стоят разными контейнерами.
*Альтернатива* — оркестратор в `tools/cms`, дёргающий `manifest:publish` в каждом контейнере: отвергнута, работает только там, где все сервисы доступны одной командой, и не решает главного — приведения ролей к каталогу.

Следствие, которое надо помнить: свежесть манифестов обеспечивает `manifest:publish` на старте контейнера. `permissions:sync` приводит каталог к тому, что **уже опубликовано**, и не видит кода, который ещё не выкачен.

### Д2. Синхронно, без очереди

Команда раскрывает роли в своём процессе, а не через `SyncSystemRolesJob`: у консольного запуска нет смысла завершаться раньше работы, а сводка обязана содержать итог, а не «поставлено в очередь». Существующая постановка job при публикации манифеста остаётся — это разные точки входа.

### Д3. Осиротевшие права: сначала отчёт, удаление — по флагу

Право, которого нет ни в одном опубликованном манифесте, по умолчанию только перечисляется в сводке. `--prune` удаляет такие права вместе с привязками к ролям. Умолчание намеренно безопасное: сервис, который на момент запуска ещё не опубликовал манифест, иначе унёс бы за собой права из всех ролей.

### Д4. Каталог прав читается из таблицы прав, а не из манифестов

Эндпоинт `GET /api/admin/v1/projects/{project}/permissions` собирает ответ из таблицы `permissions` — там уже лежат `label` и `group`, записанные каталогом. Сервис выводится из префикса ключа (`content.posts.view` → `content`). Разбор JSON манифестов на каждый запрос не нужен.

Каталог фильтруется по включённым сервисам проекта: в чекбоксах не должно быть прав сервиса, который на проекте выключен, иначе оператор соберёт роль, которая ничего не открывает. Право закрыто `auth.roles.view` — тем же, что и список ролей.

### Д5. Роль на сервис

Шаблоны `cms-auth.system_roles` приводятся к составу сервисов платформы:

| Роль | Шаблон | Назначение |
| --- | --- | --- |
| `owner` | `*` | владелец проекта |
| `admin` | `*` | администратор проекта |
| `editor` | `content.*` | контент целиком, включая ресёрч и инструкции |
| `analyst` | `analytics.*` | аналитика |
| `billing` | `pay.*` | платежи, подписки, тарифы |
| `licensing` | `pay.licensing.*` | организации, лицензии, релизы |
| `viewer` | `*.view` | просмотр всего доступного |

Имя роли совпадает с ключом сервиса там, где роль покрывает ровно один сервис. Шаблон роли `licensing` — `pay.licensing.*`, а не `licensing.*`: права модуля объявлены `PayManifest` (Д2 манифеста лицензирования), имена прав не мигрируют, поэтому шаблон ссылается на фактический префикс. Как следствие, `billing` (`pay.*`) включает и права лицензирования. Под `auth` отдельной роли нет: управление доступом, участниками и ключами — это и есть `owner`/`admin`, роль «управляю только доступом» никем не запрошена и заводить её незачем.

### Д6. Системные роли в консоли — только чтение

Ограничение уже реализовано `RolePolicy` на бэкенде; интерфейс показывает состав системной роли, но не даёт править и удалять. Признак «системная» приходит в ресурсе роли — консоль не сверяет имена со своим списком.

### Д7. Экран — вкладка в разделе «Команда»

Раздел «Команда» получает две вкладки: «Участники» (текущий экран без изменений) и «Роли». Роли — список карточек с названием и числом прав; создание и правка — диалог с полем названия и чекбоксами прав, сгруппированными по `group` из каталога. Компоненты берутся из склада `source-admin` (вкладки, чекбоксы, диалог, карточки); собственный только сам диалог роли — его в складе нет. Перенесённые файлы зеркалируются обратно в склад тем же коммитом.
*Альтернатива* — отдельный раздел «Роли» в меню: отвергнута, оператор управляет доступом в одном месте, а пункт меню под экран, который открывают раз в месяц, засоряет навигацию.

### Д8. Кэши сбрасываются командой так же, как правкой роли

После синхронизации команда делает то же, что `UpdateRolePermissionsHandler`: сбрасывает кэш прав spatie, поднимает версию bootstrap-кэша и рассылает `cacheBust` вниз по сервисам. Иначе новые права появятся в консоли только после истечения TTL — и «синхронизировал, а ничего не изменилось» станет штатным поведением.

## Risks / Trade-offs

- [`--prune` удаляет право у всех ролей, включая кастомные] → умолчание — отчёт без удаления; в сводке перечисляются права и роли, которых коснётся удаление, чтобы решение принимал человек.
- [Синхронный проход по всем проектам растёт линейно с их числом] → раскрытие ролей — несколько запросов на проект; при сотнях проектов команда занимает секунды, а не минуты, и запускается на выкате, а не по запросу оператора.
- [Новая роль `billing`/`licensing` не появится у существующих проектов сама] → она и есть работа команды: `permissions:sync` создаёт недостающие системные роли во всех проектах.
- [Каталог, отфильтрованный по включённым сервисам, скрывает права уже собранной роли] → состав роли отдаётся полностью и при выключенном сервисе; фильтр действует только на список доступных для добавления.
- [Экран ролей — новая поверхность в консоли, расходящаяся со складом] → в склад переносится только то, что оттуда взято; диалог роли остаётся собственным компонентом консоли, как редакторы платформы.

## Migration Plan

1. Команда и эндпоинт добавляются независимо: до правок конфига `permissions:sync` просто приводит состояние к текущим шаблонам.
2. Новые шаблоны ролей применяются тем же запуском команды на выкате — миграций данных нет, роли создаются идемпотентно.
3. Консоль подключается после эндпоинта каталога; до этого раздел «Команда» работает как сейчас.
4. Откат — возврат шаблонов в config и повторный `permissions:sync`; лишние роли снимаются вручную, данные проектов не затрагиваются.
