# pay-service

## Purpose

Отдельный сервис приёма платежей на проект: единоразовые платежи и подписки с полным управлением жизненным циклом (отмена, возобновление, приостановка, удаление), каталог тарифных планов с опциями и возможностями, провайдеры через адаптер, идемпотентные вебхуки. Аутентификация и права — через auth-service.

## ADDED Requirements

### Requirement: Авторизация через auth-service

Admin-запросы SHALL проверяться по операторскому токену и правам `pay.*` через introspection auth-service; public-запросы — по API-ключу проекта или токену пользователя сайта. Для проекта с выключенным pay-сервисом маршруты SHALL возвращать 404.

#### Scenario: Оператор без права

- WHEN оператор без права возврата пытается сделать refund
- THEN возвращается 403

### Requirement: Тарифные планы, опции и возможности

Admin API SHALL поддерживать CRUD тарифных планов проекта (код, название, цена в минорных единицах + валюта, интервал биллинга), их опций (лимиты и значения) и возможностей (features), привязку возможностей к планам. Публичное API SHALL отдавать каталог активных планов с опциями и возможностями. План, на который есть подписки, MUST NOT удаляться физически — только архивироваться.

#### Scenario: Каталог планов для сайта

- WHEN сайт запрашивает планы по API-ключу
- THEN возвращаются активные планы проекта с ценами в минорных единицах, опциями и возможностями

#### Scenario: Удаление плана с подписками

- WHEN оператор удаляет план с активными подписками
- THEN план архивируется, существующие подписки продолжают работать

### Requirement: Единоразовые платежи

Сервис SHALL создавать платёж (сумма в минорных единицах, валюта, назначение), проводить его через провайдера и вести статусы `created → pending → succeeded | failed | canceled` с переходами, определёнными статус-машиной; недопустимые переходы отклоняются. Каждое движение денег SHALL записываться в append-only леджер транзакций. Создание платежа SHALL быть идемпотентным по ключу идемпотентности. Возврат (полный/частичный) SHALL поддерживаться с правом оператора.

#### Scenario: Успешный платёж

- WHEN платёж подтверждён провайдером
- THEN статус становится succeeded, в леджере появляется транзакция, событие уходит в аналитику

#### Scenario: Повтор создания с тем же ключом

- WHEN создание платежа повторяется с тем же ключом идемпотентности
- THEN возвращается существующий платёж, второй не создаётся

### Requirement: Подписки

Сервис SHALL оформлять подписку пользователя проекта на план и вести её жизненный цикл: **отменить** (действует до конца оплаченного периода), **возобновить** (после отмены или приостановки), **приостановить** (биллинг и доступ замораживаются), **удалить** (soft-delete, история сохраняется). Продление SHALL выполняться автоматически по интервалу плана фоновой джобой; неуспешное продление переводит подписку в проблемный статус с повторными попытками. Статус подписки и её план SHALL быть доступны сайту по публичному API.

#### Scenario: Отмена и возобновление

- WHEN пользователь отменяет подписку, а затем возобновляет её до конца оплаченного периода
- THEN после отмены доступ сохраняется до конца периода, после возобновления автопродление снова активно

#### Scenario: Приостановка

- WHEN подписка приостановлена
- THEN продления не выполняются и доступ по подписке неактивен до возобновления

#### Scenario: Удаление

- WHEN оператор удаляет подписку
- THEN она скрывается из активных (soft-delete), леджер и история сохраняются

#### Scenario: Автопродление

- WHEN наступает конец оплаченного периода активной подписки
- THEN создаётся платёж продления; при успехе период продлевается, при неудаче статус проблемный и выполняются повторные попытки

### Requirement: Провайдеры через адаптер

Провайдеры платежей SHALL подключаться через единый интерфейс-адаптер; конфигурация провайдера — на проект, секреты зашифрованы. С первого дня SHALL существовать ручной провайдер (оплата по счёту, подтверждается оператором) и null-провайдер для тестов.

#### Scenario: Ручное подтверждение

- WHEN оператор подтверждает оплату счёта в ручном провайдере
- THEN платёж переходит в succeeded тем же путём, что и у онлайн-провайдера

### Requirement: Идемпотентные вебхуки

`POST /webhooks/{provider}` SHALL проверять подпись провайдера (провал → 401, ничего не пишется), сохранять сырое событие с уникальностью по (provider, external_id) — дубль получает 200 без повторной обработки — и отвечать 200 быстро; обработка идёт в фоновой очереди с ретраями. Бизнес-логика в HTTP-запросе вебхука MUST NOT выполняться.

#### Scenario: Дубль вебхука

- WHEN провайдер присылает одно событие дважды
- THEN второй запрос получает 200, эффект применяется один раз

#### Scenario: Неверная подпись

- WHEN вебхук приходит с неверной подписью
- THEN возвращается 401 и событие не сохраняется

### Requirement: События платежей в аналитику

События (`payment.succeeded`, `payment.failed`, оформление/отмена/возобновление/приостановка подписки) SHALL уходить в analytics-service через `Analytics::push` с ключом пользователя и суммами в минорных единицах; недоступность аналитики MUST NOT влиять на платежи.

#### Scenario: История платежей пользователя

- WHEN пользователь оплатил подписку и позже отменил её
- THEN его хронология в аналитике содержит оба события
