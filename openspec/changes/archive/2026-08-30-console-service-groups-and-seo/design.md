## Context

См. `proposal.md` — Why. Что важно из текущего состояния:

- Каталог разделов консоли задан вручную: `frontends/admin/src/lib/admin/sidebar-config.ts` (группы, пункты, иконки) и `lib/admin/data-source/section-access.ts` (`CONSOLE_SECTION_KEYS` + `SECTION_REQUIREMENTS`: раздел → `{service, permission}`). Снимок доступа пишется в cookie и localStorage, читается сайдбаром и `proxy.ts`.
- `licensing` — самостоятельный переключаемый сервис: `ServiceName::toggleable()`, `default_enabled_services`, миграция бэкфилла `2026_08_28_000000_backfill_licensing_project_service.php`, гейт `EnsureServiceEnabled:licensing` на своих admin-маршрутах.
- Платёжный API готов целиком (`pay/plans`, `pay/payments`, `pay/subscriptions`), экранов в консоли нет. Списки платежей и подписок сейчас без фильтров.
- SEO хранится полиморфно в `seo_meta` (`Cms\Content\Domain\Models\SeoMeta`), правится по одной записи через `content/seo/{type}/{id}`. Списочного API нет.
- Генерация SEO по AI уже есть: `Cms\Research\Application\Actions\ComposePostSeoAction` + инструкция `InstructCategory::PostSeo` из `SystemInstructCatalog`. Пакет `content` от `ai` не зависит, `research` зависит от `ai`, `content`, `instructs`.
- Фоновые задачи с прогрессом — `Cms\Shared\BackgroundTasks` (`BackgroundTaskKind`, `TaskProgress`), эталон постановки — `StartPostRebuildHandler`.
- Сборка проекта по AI живёт в `components/pages/dashboard/sections/ProjectCard/`, а раздел «Основные» настроек уже сохраняет название и описание проекта той же формой (`GeneralSection` + `useSaveGeneralSettingsMutation`).

## Goals / Non-Goals

**Goals:**

- Группы сайдбара собираются по сервису платформы, а не по группам исходной вёрстки.
- Лицензирование включается вместе с оплатой, без отдельного переключателя и без переименования прав.
- SEO проекта видно и правится одним списком, а не по карточкам сущностей.
- Сборка проекта по AI не зависит от сервиса аналитики.

**Non-Goals:**

- Не меняем состав и семантику прав платформы.
- Не трогаем публичное API контента и оплаты, вебхуки провайдеров и публичную валидацию лицензий.
- Не добавляем раздел «Страницы» и раздел медиа: в группе «Контент» — только уже существующие разделы плюс SEO.
- Не переносим экраны из склада, которых нет в платформе (заказы, товары, промо).

## Decisions

### Р1. Группа сайдбара — поле пункта, а не отдельная структура

Каталог `sidebar-config.ts` остаётся плоским списком групп, но состав групп переписывается под сервисы: «Обзор», «Контент», «Оплата», «Рабочее пространство». Фильтрация по снимку доступа (`selectVisibleSections`) уже скрывает пустые группы — новой машинерии не нужно.

Альтернатива: выводить группы из манифестов сервисов (`NavigationItem.group`). Отклонено: манифесты сейчас не участвуют в сборке меню консоли (`SECTION_REQUIREMENTS` задан явно, потому что маршруты манифестов и маршруты консоли не совпадают), а переход на них — отдельная задача, не относящаяся к этому изменению.

### Р2. Ключи разделов расширяются, требования задаются явно

В `CONSOLE_SECTION_KEYS` добавляются `payments`, `subscriptions`, `plans`, `license-plans`, `licenses`, `organizations`, `releases`, `seo`; `licensing` удаляется. В `SECTION_REQUIREMENTS` каждому — своя строка:

| Раздел | Сервис | Право |
| --- | --- | --- |
| `payments` | `pay` | `pay.payments.view` |
| `subscriptions` | `pay` | `pay.subscriptions.view` |
| `plans` | `pay` | `pay.plans.view` |
| `license-plans`, `licenses`, `organizations`, `releases` | `pay` | `pay.licensing.view` |
| `seo` | `content` | `content.seo.manage` |

Ключ раздела равен сегменту маршрута (`sectionKeyOfPath`), поэтому маршруты консоли называются так же: `/admin/payments`, `/admin/license-plans` и т. д.

У SEO нет отдельного права просмотра — в платформе объявлено только `content.seo.manage`. Заводить новое право ради раздела не будем: раздел целиком про правку.

### Р3. Лицензирование гейтится сервисом `pay`

`ServiceName::Licensing` остаётся в перечислении (ключ манифеста, ключ гейта прежних записей), но уходит из `ServiceName::toggleable()` и из `default_enabled_services`. `routes/admin.php` лицензирования переходит на `EnsureServiceEnabled:pay`. Манифест `licensing` продолжает публиковаться — меняется только его навигация: один пункт вместо четырёх.

Альтернатива: удалить сервис `licensing` целиком и слить манифесты. Отклонено: манифест — граница пакета, а слияние потянуло бы зависимость `pay → licensing`, которой в коде намеренно нет (`PayManifest` объявляет права лицензирования строками).

### Р4. Миграция: проектам с включённым `licensing` включается `pay`

Новая миграция в `cms/auth`: для каждого проекта, где `project_services(licensing, enabled = true)`, вставляется или включается строка `pay`. Строки `licensing` не удаляются — они перестают читаться, и откат миграции возвращает прежнее поведение без потери данных.

Без этого шага проект, где оплата была выключена, а лицензирование включено, потерял бы разделы лицензирования из консоли.

### Р5. Разбиение раздела лицензирования — по существующим секциям

`components/pages/licensing/sections/{Plans,Licenses,Organizations,Releases}Section.tsx` становятся страницами `app/admin/{license-plans,licenses,organizations,releases}`. Вёрстка секций не переписывается: снимается только обёртка вкладок, добавляется `PageHeader` каждой страницы. Адрес `/admin/licensing` удаляется.

### Р6. Новые экраны оплаты — из склада `source-admin`

Таблица транзакций собирается из `frontends/source-admin/src/components/pages/orders/*` (таблица, колонки, статус-бейдж, модалка деталей), подписки и планы — из тех же кирпичей `components/ui/**`. Перенесённые файлы обязаны совпадать со складом побайтово; всё, что меняется под платформу, тем же коммитом уезжает обратно в склад.

### Р7. Фильтры списков оплаты добавляются минимально

`ListSubscriptionsQuery` получает необязательный отбор по `subject_type` (нужен для «подписок на планы лицензий»), `ListPaymentsQuery` — по статусу. Фильтры принимаются `FormRequest` → DTO, как везде. Больше фильтров сейчас не заводим: второго случая нет.

### Р8. Каталог SEO читается в `content`, пересборка запускается в `research`

- `GET content/seo` — новый `ListProjectSeoQuery` в `cms/content`: `UNION ALL` по постам, страницам и категориям с `LEFT JOIN seo_meta`, отбор по типу, сортировка по типу/названию/дате изменения, постраничная навигация. `LEFT JOIN` нужен, чтобы сущность без SEO попадала в каталог пустой строкой.
- `POST content/seo/rebuild` — в `cms/research`, рядом с `posts/{post}/rebuild`: там уже живут AI, инструкции и `ComposePostSeoAction`.

Альтернатива: собрать каталог тремя запросами и склеить в PHP. Отклонено: сортировка и пагинация «поперёк» типов на склейке в памяти ломаются на первом же проекте с тысячей постов.

Альтернатива: положить пересборку в `content`. Отклонено: `content` не зависит от `ai` и `instructs`, и заводить эту зависимость ради одной операции — разворот текущих границ пакетов.

### Р9. Пересборка — фоновая задача с собственным видом

Добавляется `BackgroundTaskKind::SeoRebuild`. Постановка — по эталону `StartPostRebuildHandler`: запись задачи заводится до `dispatch`, `subject_type = 'project'`, `subject_id = project_id`. Job получает `project_id`, список идентификаторов сущностей (пустой — все) и `task_id`; отказ по одной сущности пишется в прогресс и не роняет задачу, `failed()` уходит в аудит. Повторный запуск при выполняющейся задаче — доменное исключение `*RuleViolation` → 422.

Консоль показывает ход через уже существующий `useTasksQuery({kind: 'seo_rebuild'})` — та же механика, что у пересборки поста.

### Р10. AI заполняет только текстовые SEO-поля

Пересборка пишет `title`, `description`, `keywords`, `og_title`, `og_description`, `twitter_card`. `canonical`, `robots`, `og_image` и `json_ld` остаются за оператором: AI не может знать канонический адрес витрины и не выдумывает файл картинки. Схема инструкции `InstructCategory::PostSeo` в `SystemInstructCatalog` расширяется тремя полями; для категорий заводится `InstructCategory::CategorySeo` (вход — название и описание категории), страницы пересобираются инструкцией поста.

Это допущение, а не требование пользователя: если «все поля» означает и `canonical`/`robots`, решение меняется — тогда AI получает базовый адрес проекта на вход, а `robots` собирается правилом, а не моделью.

### Р11. Карточка проекта сливается с разделом «Основные», а не переносится вторым блоком

`GeneralSection` уже правит название и описание проекта. Поэтому из `ProjectCard` в раздел переезжают идентификатор проекта (строка сверху раздела, с копированием) и `BuildoutPanel`; дублирующие поля названия и описания не переносятся. `components/pages/dashboard/sections/ProjectCard/` удаляется вместе с использованием на дашборде.

Право на сборку — `auth.projects.manage` (как сейчас в `ProjectBuildoutController`), то есть действие видно тем же операторам, что и раньше, независимо от сервиса аналитики.

## Risks / Trade-offs

- **Проект с включённым лицензированием и выключенной оплатой теряет разделы** → миграция Р4 включает `pay` таким проектам; шаг обязателен и выполняется до выката консоли.
- **Закладки операторов на `/admin/licensing` перестают работать** → адрес удаляется без редиректа: раздел заменён четырьмя, однозначной цели у редиректа нет. Оператор попадает на страницу отказа, разделы видны в меню.
- **`UNION ALL` по трём таблицам с сортировкой по названию может быть медленным** → отбор всегда идёт по `project_id` (индекс есть), пагинация — постраничная; при появлении реальной нагрузки каталог выносится в отдельную проекцию, но не «на вырост».
- **AI-пересборка всех сущностей — длинная задача и расход токенов** → одна задача на проект, повторный запуск отклоняется; в консоли видно, что задача идёт, и на каком она этапе.
- **Расширение схемы `PostSeo`** меняет поведение уже существующей генерации поста: пост будет получать ещё и og-поля → это ожидаемое улучшение, но заметное; отражено в тестах пересборки поста.
- **Разделов в меню становится заметно больше** (семь в группе «Оплата») → группа целиком скрыта, пока сервис выключен, а внутри пункты отсекаются правами.

## Migration Plan

1. Выкатить бэкенд: `toggleable()` без `licensing`, гейт лицензирования по `pay`, миграция включения `pay`, каталог SEO, пересборка SEO.
2. Прогнать миграции (`./tools/cms migrate`) — включение `pay` проектам с лицензированием.
3. Перезапустить `*-service`, `*-worker`, `*-scheduler`: новый вид фоновой задачи и новые маршруты.
4. Выкатить консоль и перезапустить `admin-front` (бандл собирается при старте).
5. Откат: вернуть прежний `toggleable()` и гейт `EnsureServiceEnabled:licensing`; строки `project_services(licensing)` не удалялись, поэтому прежняя видимость восстанавливается без правки данных.

## Open Questions

- Нужен ли раздел «Страницы» в группе «Контент». Сейчас страницы правятся только через API; добавление раздела — отдельная задача и на состав этой группы не влияет.
