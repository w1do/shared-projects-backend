# pay-service — delta

## MODIFIED Requirements

### Requirement: Идемпотентные вебхуки

`POST /webhooks/{provider}` SHALL проверять подпись провайдера (провал → 401, ничего не пишется), сохранять сырое событие с уникальностью по (provider, external_id) — дубль получает 200 без повторной обработки — и отвечать 200 быстро; обработка идёт в фоновой очереди с ретраями. Бизнес-логика в HTTP-запросе вебхука MUST NOT выполняться. Приём SHALL работать без контекста проекта; событие SHALL записываться с `project_id`, определяемым по платежу из payload (сразу при регистрации, если платёж резолвится, иначе — при обработке в очереди). События без резолвируемого платежа SHALL сохраняться с `project_id = NULL` и статусом `failed`.

#### Scenario: Дубль вебхука

- WHEN провайдер присылает одно событие дважды
- THEN второй запрос получает 200, эффект применяется один раз

#### Scenario: Неверная подпись

- WHEN вебхук приходит с неверной подписью
- THEN возвращается 401 и событие не сохраняется

#### Scenario: Вебхук известного платежа

- WHEN приходит вебхук с payment_id существующего платежа
- THEN событие записано, после обработки его project_id равен проекту платежа

#### Scenario: Вебхук неизвестного платежа

- WHEN приходит вебхук с неизвестным payment_id
- THEN ответ 200 {"received": true}, событие сохранено со статусом failed и project_id NULL

### Requirement: Тарифные планы, опции и возможности

Admin API SHALL поддерживать CRUD тарифных планов проекта (код, название, цена в минорных единицах + валюта, интервал биллинга), их опций (лимиты и значения) и возможностей (features), привязку возможностей к планам. Публичное API SHALL отдавать каталог активных планов с опциями и возможностями. План, на который есть подписки, MUST NOT удаляться физически — только архивироваться. Валюта плана SHALL нормализоваться к верхнему регистру при сохранении; исторические данные SHALL быть приведены миграцией; ответы API SHALL отдавать валюту в верхнем регистре.

#### Scenario: Каталог планов для сайта

- WHEN сайт запрашивает планы по API-ключу
- THEN возвращаются активные планы проекта с ценами в минорных единицах, опциями и возможностями

#### Scenario: Удаление плана с подписками

- WHEN оператор удаляет план с активными подписками
- THEN план архивируется, существующие подписки продолжают работать

#### Scenario: План с валютой в нижнем регистре

- WHEN оператор создаёт план с currency "usd"
- THEN план сохраняется и отдаётся с currency "USD", подписка и возврат по нему работают

### Requirement: Единоразовые платежи

Сервис SHALL создавать платёж (сумма в минорных единицах, валюта, назначение), проводить его через провайдера и вести статусы `created → pending → succeeded | failed | canceled` с переходами, определёнными статус-машиной; недопустимые переходы отклоняются. Каждое движение денег SHALL записываться в append-only леджер транзакций. Создание платежа SHALL быть идемпотентным по ключу идемпотентности. Возврат (полный/частичный) SHALL поддерживаться с правом оператора. Провайдеры SHALL конфигурироваться на проект через `provider_accounts` (зашифрованные credentials); адаптеры без конфигурации работают как прежде. Если запись возврата упала после успешного возврата у провайдера, платформа SHALL оставлять восстановимый след (критический лог с payment_id, провайдером и суммой) — молчаливая потеря факта возврата MUST NOT происходить.

#### Scenario: Успешный платёж

- WHEN платёж подтверждён провайдером
- THEN статус становится succeeded, в леджере появляется транзакция, событие уходит в аналитику

#### Scenario: Повтор создания с тем же ключом

- WHEN создание платежа повторяется с тем же ключом идемпотентности
- THEN возвращается существующий платёж, второй не создаётся

#### Scenario: Сбой записи после возврата провайдером

- WHEN провайдер подтвердил возврат, а запись в БД упала после всех повторов
- THEN в журнале остаётся критическая запись с полным контекстом возврата
