# Панель управления (`frontends/admin`)

Панель — перенесённая вёрстка из `frontends/source-admin`
(Next.js 16 + React 19 + Tailwind v4), запускаемая на Bun. Подключение к API
платформы сделано только в слое данных вёрстки (`src/lib/admin/data-source/*`,
`src/lib/admin/services/*`); разметка, стили и структура компонентов не
изменялись. Тексты видимых разделов локализованы (русский — язык по умолчанию)
через реестр `console.*` — см. «Язык консоли» ниже.

## Язык консоли и переопределения текстов

Все UI-строки видимых разделов берутся из реестра
`src/lib/admin/console-texts.ts`: плоская карта типизированных ключей
`console.*` с русскими значениями по умолчанию. Компоненты получают тексты
через `t(key)` / `tf(key, params)` или хук `useConsoleText()` — строковых
литералов в живых поверхностях нет. Скрытые демо-разделы шаблона не
русифицированы: они не видны оператору.

Поверх реестра накладываются переопределения из **словаря переводов проекта**
(тот же словарь, что на вкладке Languages): после входа и при каждом успешном
`bootstrap` панель запрашивает плоскую выдачу
`GET /content/translations?locale=<bootstrap.user.locale>`, отбирает ключи с
префиксом `console.` и применяет их поверх значений по умолчанию
(`data-source/platform/console-texts-loader.ts`). Так любой текст консоли
можно переопределить или перевести на язык оператора, добавив в словарь ключ
вида `console.nav.settings`.

- Локаль оператора — `bootstrap.user.locale` (по умолчанию `ru`).
- Кэш переопределений — localStorage `console_texts:<локаль>:<версия>`;
  версия — `bootstrap.translations_version`, растёт при любой записи словаря,
  поэтому кэш инвалидируется сам.
- Словарь недоступен (content выключен, запрос упал) — панель молча работает
  на русских значениях по умолчанию.
- Отсутствие ключа в словаре — значение по умолчанию, а не пустая строка.

Юнит-тесты реестра — `console-texts.test.ts`; сценарий переопределения —
`e2e/tests/localization.spec.ts`.

## Запуск

```bash
cd frontends/admin
bun install
bun run dev                  # разработка
bun run build && bun run start   # production
```

Вместе со стеком: `./tools/cms up` — панель поднимается сервисом `admin-front`
(образ `oven/bun`) и отдаётся через gateway на том же порту, что и API
(`/` → `/admin`).

Переменные — `infra/services/admin-front/.env`:

| Переменная | Назначение |
| --- | --- |
| `NEXT_PUBLIC_ADMIN_DATA_SOURCE` | `api` — данные платформы, `mock` — демо-данные вёрстки |
| `NEXT_PUBLIC_ADMIN_API_BASE_URL` | базовый URL API; пусто — тот же origin, что и панель |
| `NEXT_PUBLIC_ADMIN_MOCK_DELAY_MS` | искусственная задержка mock-данных |
| `ADMIN_INTERNAL_API_BASE_URL` | базовый URL для серверных запросов внутри docker-сети |

## Вход оператора

Вход идёт против auth-service: `POST /api/admin/v1/auth/login` (email + пароль),
профиль — `GET /api/admin/v1/me`, текущий проект — `GET /api/admin/v1/bootstrap`.
Сессия хранится так, как её ждёт вёрстка: cookie `auth_token` (он же Bearer-токен
платформы), `auth_role`, `project_key` и `current_user` в localStorage.
Раздел `/admin/**` без cookie `auth_token` уводит на `/login` (`src/proxy.ts`).

## Видимость разделов

Состав меню не статичен: он собирается из ответа `GET /api/admin/v1/bootstrap`.
Раздел показывается, **только если его сервис включён для проекта и у оператора
есть объявленное для раздела право**. Супер-администратор (`permissions: ["*"]`)
видит все разделы включённых сервисов.

| Раздел | Сервис | Право |
| --- | --- | --- |
| `/admin` (Dashboard) | `analytics` | `analytics.reports.view` |
| `/admin/blogs` | `content` | `content.posts.view` |
| `/admin/categories` | `content` | `content.categories.view` |
| `/admin/customers` | `auth` (ядро) | `auth.users.view` |
| `/admin/team` | `auth` (ядро) | `auth.members.view` |
| `/admin/settings` | `auth` (ядро) | `auth.settings.view` |

`auth` — сервис-ядро: `cms-auth.php` объявляет переключаемыми только
`['content', 'analytics', 'pay']`, поэтому `auth` не приходит в
`bootstrap.services[]` и выключить его нельзя. Его разделы проверяются только по
праву оператора (`CORE_SERVICES` в `section-access.ts`). Для переключаемых
сервисов действует полное правило «включён + есть право».

Разделы, которым не соответствует ни один сервис платформы, скрыты всегда:
`products`, `variants`, `brands`, `collections`, `inventory`, `orders`,
`campaigns`, `promotions`, `support`, `notifications`. Их страницы, компоненты,
маршруты и демо-данные **остаются в репозитории нетронутыми** — они просто не
отображаются.

Как это устроено:

- карта требований и вычисление видимых ключей — `src/lib/admin/data-source/section-access.ts`;
- меню и быстрые действия — `useVisibleNavigation()` (`src/lib/admin/data-source/use-visible-navigation.ts`),
  порядок, группы, подписи и иконки берутся из `sidebar-config.ts` без изменений,
  группа без видимых пунктов не отображается;
- снимок доступа пишется при входе и при каждом успешном `bootstrap` в cookie
  `console_sections` (для серверного guard'а) и в localStorage (для рендера меню
  без ожидания сети); живёт столько же, сколько сессия;
- прямой переход на скрытый раздел уводит на существующую страницу
  `/admin/unauthorized` (`src/proxy.ts`). Отсутствующая cookie трактуется как
  «снимок не готов» и навигацию не блокирует — доступ к данным всё равно закрыт
  правами на бекенде.

**Чтобы вернуть раздел**, когда в платформе появится соответствующий сервис,
достаточно одной строки в `SECTION_REQUIREMENTS` (`section-access.ts`):

```ts
orders: { service: "commerce", permission: "commerce.orders.view" },
```

Юнит-тесты карты и селекторов — `src/lib/admin/data-source/section-access.test.ts`,
запуск: `npm test` в `frontends/admin` (штатный `node --test`).

## Разделы: живые данные и демо-данные

| Раздел | Источник |
| --- | --- |
| `dashboard` | analytics-service: KPI, обзор выручки, топ-страницы за период; «Свежие материалы» — реальные посты content-service. Демо-секции шаблона (бестселлеры, остатки, последние заказы, кампании, бренды, «продажи по категориям») с живой страницы убраны — их данных в платформе нет |
| `blogs` | content-service: посты проекта — список со статусами и отбором, создание (черновиком), правка, привязка к категориям проекта, публикация/архив по статус-машине, ревизии с восстановлением. KPI-карточки считаются из реального списка, без зашитых дельт и трендов |
| `categories` | content-service: дерево категорий (nested set) — вложенность видна в списке, создание с выбором родителя, перемещение поддеревьев, удаление с предупреждением. Торговых метрик нет: карточки аналитики и колонки «Выручка»/«Рост г/г» убраны, вместо счётчика товаров — счётчик вложенных категорий; PDF-отчёт — только структура дерева |
| `customers` | auth-service: пользователи проекта, блокировка/разблокировка, удаление. KPI: всего, активные, заблокированные, доля активных; уровней лояльности и денежных метрик у платформы нет — колонка и фильтр лояльности в живом режиме не показываются |
| `team` | auth-service: участники проекта, приглашение, назначение роли, удаление |
| `settings` | auth-service: имя проекта и состав операторов; язык по умолчанию — site-settings (auth-service); вкладка «Платежи» — провайдер Platega из pay-service (pay/settings); вкладка «Языки» — локали и словарь переводов; вкладка «Сервисы» — включение сервисов проекта. Секции «уведомления», «безопасность» — демо-данные |
| `products`, `variants`, `inventory`, `brands`, `collections` | демо-данные: в платформе нет каталога товаров |
| `orders` | демо-данные: в платформе нет модуля заказов |
| `promotions`, `campaigns` | демо-данные: в платформе нет промо-модуля |
| `notifications`, `support` | демо-данные: в платформе нет соответствующих сервисов |

Разделы на демо-данных работают штатно и в режиме `api`: слой данных для них
возвращает данные вёрстки, а не пустые экраны. При этом в меню они не
показываются — см. «Видимость разделов» выше.

## Возможности платформы без экрана в вёрстке

В вёрстке нет соответствующих экранов, поэтому эти операции доступны только на
уровне слоя данных (`src/lib/admin/services`), без добавления новых страниц:

- SEO-метаданные контента, включая JSON-LD — `content-domain/seo.ts`
  (`content/seo/{type}/{id}`). Поля, которые несёт форма поста (заголовок,
  подзаголовок, теги, обложка), пишутся в SEO при сохранении поста.
- API-ключи проекта (выдача/отзыв) — `projectApiKeys` в `content-domain/settings.ts`.
- Настройки отдельных сервисов (`getSettings`/`putSettings`) — `projectServices`
  там же; включение/выключение сервисов имеет экран — см. «Управление
  сервисами» ниже.
- Страницы (`pages`) и медиа content-service.

## Управление сервисами в панели

Settings → вкладка **Сервисы** (`ServicesSection`, собрана из шаблонных
`SettingsSection` + `SettingsToggleRow`): галочки переключаемых сервисов проекта
(`content`, `analytics`, `pay`) поверх `projectServices.list/toggle`
(`PUT /projects/{key}/services/{service}`). `auth` — ядро, платформа не отдаёт
его в списке, выключить его нельзя.

- Просмотр вкладки гейтится правом раздела settings (`auth.settings.view`);
  переключатели активны только при праве `auth.services.manage` в
  `bootstrap.permissions`, иначе состояние доступно только для чтения.
- Переключение оптимистичное: при ошибке сохранения переключатель
  откатывается к фактическому состоянию и оператор видит toast с ошибкой.
- После успешного переключения `bootstrap` перечитывается: снимок
  `console_sections` переписывается, подписка в `useVisibleNavigation()`
  перечитывает его — сайдбар и быстрые действия отражают состав сервисов
  **сразу**, без повторного входа. Состояние переживает перезагрузку и
  повторный вход.

Сценарии — `e2e/tests/console-navigation.spec.ts` («переключение сервисов из
консоли»); юнит-тест подписки на снимок — `section-access.test.ts`.

## Роли участников проекта

Вёрстка оперирует тройкой `admin / manager / staff`, платформа заводит на проект
роли `owner, admin, editor, analyst, viewer`. Сопоставление — в
`data-source/platform/auth.ts` (`toPlatformRole` / `toConsoleRole`):

| Панель | Платформа |
| --- | --- |
| `admin` | `admin` (и `owner` — при отображении) |
| `manager` | `editor` |
| `staff` | `viewer` |

Приглашение в `/team` заводит оператора, которого ещё нет: аккаунт создаётся с
непригодным для входа паролем, войти приглашённый может только через сброс
пароля по своему email. Неизвестная роль отклоняется **до** создания аккаунта,
поэтому аккаунтов-сирот не остаётся.

Диалог «Invite teammate» из быстрых действий и раздела Settings пока остаётся
демонстрационным: он не обращается к API. Рабочий путь приглашения — раздел
`/team`.

## Демо-данные для разработки

Сидер `apps/content-service/database/seeders/DemoContentSeeder.php` заводит
11 категорий (дерево из трёх уровней) и 2 новости (опубликованная + черновик):

```bash
./tools/cms seed-demo            # проект demo
./tools/cms seed-demo <key>      # другой проект
```

Команда берёт идентификатор проекта из auth-service и передаёт его сидеру
через `DEMO_PROJECT_ID` — сидер требует его явно. Угадывать проект по уже
существующему контенту нельзя: `tools/smoke.sh` пересоздаёт проект с новым
идентификатором, и молчаливый запасной вариант засеивал данные в давно
несуществующий проект. Сидер идемпотентен — повторный прогон не дублирует.

## Контент: дерево категорий и посты

**Категории — дерево с перетаскиванием.** Список (`TreeTable`,
`ui/data-display/tree-table.tsx`) показывает вложенность отступами и позволяет
перетаскивать строки: бросок **на середину строки** вкладывает узел в неё,
бросок **в верхнюю/нижнюю треть** ставит соседом в этой позиции (линия-вставка и
подсветка различают зоны). Поддерево всегда следует за узлом; порядок соседей
сохраняется платформой (`position` в операции `move`). Сам узел и его поддерево
как цель подсвечиваются запрещёнными — замкнуть дерево на себя нельзя. Ветви
сворачиваются шевроном. При активном поиске перетаскивание выключено: порядок
отфильтрованного списка не отражает соседства. Пагинации в режиме api нет —
дерево показывается целиком; mock-режим сохраняет прежнюю плоскую таблицу.

Альтернатива без мыши — действие «Move to…» в меню строки (та же операция
платформы). Родитель в формах и диалоге выбирается селектом категорий
(`CategoryTreeSelect`, `ui/inputs/category-tree-select.tsx`): вложенное дерево с
поиском, у найденного узла видна цепочка предков; недопустимые узлы недоступны.
Тот же селект в множественном режиме привязывает пост к категориям.
**Удаление снимает всё поддерево**; посты при этом сохраняются и теряют только
привязку — диалог предупреждает об этом до подтверждения.

**Посты.** Создание сохраняет пост **черновиком** — публикация отдельное
действие в карточке «Post status» на странице редактирования; допустимость
переходов решает статус-машина платформы (черновик → публикация, публикация →
архив, архив → черновик). Привязка к категориям проекта — чекбоксы с деревом в
форме. Каждое сохранение создаёт ревизию; прежнюю версию можно восстановить из
той же карточки. Slug задаётся при создании и при правке заголовка не меняется.
«Удаление» поста в списке — перевод в архив: удалять посты платформа не умеет
(маршрута DELETE нет), из черновика архив недоступен и попытка вернёт отказ.

Сценарии контента — `e2e/tests/content-management.spec.ts` (дерево, перемещение
через диалог, запрет цикла, жизненный цикл поста с ревизиями) и
`e2e/tests/category-tree-dnd.spec.ts` (перетаскивание: вложение, порядок,
запрет, отказ платформы; селект с поиском). Тестовые данные создаются под
уникальными именами; категории убираются удалением, посты — архивом.

## Сценарии панели (Playwright)

Визуальные требования — состав меню, отказ по прямому адресу, реакция на смену
состава сервисов — проверяются сценариями Playwright в `e2e/`. Они идут против
поднятого стека через gateway, то есть против той же production-сборки панели,
которую видит оператор.

```bash
./tools/cms up                # стек должен быть поднят
./tools/smoke.sh              # демо-окружение: оператор, проект demo, сервисы

./tools/cms e2e               # headless
./tools/cms e2e --headed      # видно на экране (нужен DISPLAY; в WSL — WSLg)
```

**После правок в `frontends/admin` перезапустите панель** — иначе сценарии
проверят прежнюю сборку:

```bash
docker restart platform-admin-front-1
```

Артефакты прогона — `e2e/.artifacts/` (в `.gitignore`): видео и снимок экрана
сохраняются для упавших сценариев, трейс — при повторной попытке.

Настройки прогона — переменные окружения: `E2E_BASE_URL` (по умолчанию
`http://localhost:8080`), `E2E_PROJECT` (`demo`), `E2E_EMAIL`, `E2E_PASSWORD`,
`E2E_HEADED=1`. Значения по умолчанию только локальные: сценарии меняют состав
сервисов проекта (и возвращают его обратно), запускать их против окружения с
реальными данными нельзя.

Первый запуск на новой машине требует системных библиотек браузера
(`libnss3`, `libnspr4`, `libasound2`):

```bash
cd e2e && sudo npx playwright install-deps chromium
```

Если `sudo` недоступен, те же библиотеки ставятся в домашний каталог без root —
`./tools/cms e2e` подхватывает их автоматически:

```bash
cd "$(mktemp -d)" && apt-get download libnss3 libnspr4 libasound2t64
for d in *.deb; do dpkg -x "$d" root; done
mkdir -p ~/.local/lib/playwright-deps
cp -a root/usr/lib/x86_64-linux-gnu/*.so* ~/.local/lib/playwright-deps/
```

## Ошибки API

`401` завершает сессию и уводит на `/login`; `403`, `422`, недоступность сервиса
и сетевые сбои поднимаются как `AdminApiError` с текстом для toast'а вёрстки —
интерфейс остаётся работоспособным.

## AI-операции платформы (`packages/cms/ai`)

Единый контракт `Cms\Ai\Domain\Contracts\AiOperations` — пять операций со
структурными ответами: `rewrite`, `normalize`, `translate` (форма
`key => {locale: value}`), `suggestCategories` (дерево), `generatePost`
(title/slug/body). Под капотом — `laravel/ai`; провайдер по умолчанию — Polza
(OpenAI-совместимый), меняется окружением без правки кода:

| Переменная | Назначение |
| --- | --- |
| `OPENAI_API_KEY` | ключ провайдера (обязателен; без него — `AiConfigurationException` до сети) |
| `OPENAI_BASE_URL` | адрес API; по умолчанию `https://polza.ai/api/v1` |
| `CMS_AI_MODEL` | модель; по умолчанию `openai/gpt-5.4-mini` (каталог: `GET /v1/models` Polza) |
| `CMS_AI_TIMEOUT` | таймаут вызова, сек |

Подключение потребителем: `composer require cms/ai` (path-репозиторий уже
настроен), инъекция `AiOperations` в конструктор. Отказы провайдера —
`AiRequestException`, невалидная форма ответа — `AiResponseException`; сырой
текст модели за границу пакета не выходит. Тесты — фейк SDK
(`StructuredAgent::fake([...])`), сети в тестах нет.

## Локализация (`packages/cms/localization`)

**Словарь переводов** проекта — `key → {locale: value}` (пример:
`nav.categories => {en: "Categories", ru: "Категории"}`):
`GET/POST/PUT/DELETE /content/translations` (права
`content.translations.view|manage`), `GET …?locale=ru` — плоский словарь с
откатом на локаль по умолчанию. Любая запись поднимает
`translations_version` в `bootstrap` (content уведомляет auth по внутреннему
каналу) — панель кэширует словарь и перечитывает его при росте версии.

**Переводимые поля.** Имя категории — spatie/laravel-translatable:
`name = {en, ru}` при едином slug. API совместим: строка в `name` кладётся в
локаль по умолчанию, набор — целиком; ответ содержит `name` (строка локали
запроса) и `name_translations` (полный набор). Локаль запроса — `?locale=…`
из объявленных у проекта, иначе первая локаль проекта.

**Автоперевод.** `POST /content/translations/translate-missing` ставит Job:
недостающие локали словаря и имён категорий заполняются операцией `translate`
пакета `cms/ai` (пачками; уже полные записи провайдера не вызывают).
Автопереводы помечены (`machine`, у категорий — `name_machine`) до ручной
правки, которая пометку снимает. Ошибка провайдера не меняет записи; повторный
запуск дозаполняет только оставшееся.

## Управление языками в панели

Settings → вкладка **Languages**:

- **Project locales** — состав локалей проекта (первая — по умолчанию),
  добавление и удаление; удаление локали не стирает сохранённые переводы.
- **Translation dictionary** — таблица словаря: поиск по ключу, значения по
  локалям, бейдж `machine` у автопереводов (снимается ручным сохранением),
  создание и удаление ключей.
- **Translate missing** — ставит фоновый автоперевод недостающих локалей
  словаря и имён категорий (нужен `OPENAI_API_KEY` в env content-service).

Форма категории в режиме api вводит имя по локалям проекта: первое поле —
локаль по умолчанию (из него slug), остальные — переводы с откатом на дефолт.
Сценарии — `e2e/tests/localization.spec.ts`.
