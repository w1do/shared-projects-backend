# Нагруженный dev-стенд (`./tools/cms seed-load`)

Демо-данные бутстрапа — один проект, десяток категорий и пара постов. На таком
объёме не видно ни курсорной пагинации, ни отчётов ClickHouse, ни переключения
проектов. `seed-load` наполняет поднятый стек реалистичным объёмом: 20 проектов
с данными всех четырёх сервисов.

```bash
./tools/cms up            # стек должен быть поднят
./tools/cms seed-load     # 20 проектов (по умолчанию)
./tools/cms seed-load 3   # столько проектов, сколько нужно
./tools/cms seed-load 0   # только очистка: убрать всё, что насеял сидер
```

Команда последовательно вызывает сеялку каждого сервиса и печатает сводку:
что создано, сколько времени занял шаг, какие шаги пропущены и почему.

## Что появляется в каждом проекте

| Сервис | Данные |
|---|---|
| auth | проект `load-NN` (локали `ru`, `en`), 3 включённых сервиса, 5 настроек сервисов и 5 настроек сайта, публичный и секретный API-ключи, 5 операторов-участников (по одному на системную роль), 200 записей аудита, 2000 пользователей сайта |
| content | 39 категорий (дерево из трёх уровней), 150 постов в разных статусах (120 русских, 30 английских переводов), 30 PNG в MinIO (~1.3 КБ каждый), 300 ключей словаря переводов |
| pay | 4 тарифа, 6 возможностей, 300 подписок (active / paused / canceled / past_due), **20 000 платежей** и 18 000 транзакций леджера, аккаунт провайдера `manual` |
| licensing | 10 организаций, 3 лицензионных плана с фичами, 8 релизов, 50 лицензий, ~100 установок |
| analytics | **100 000 событий** в ClickHouse за последние 350 дней: просмотры страниц и события платежей с суммами |

Данные связные: у платежа есть существующие подписка, тариф и плательщик —
пользователь сайта того же проекта; пост лежит в существующей категории.

Операторы проектов входят в панель с паролем `secret-123`, адрес —
`load-NN-<роль>@example.test` (например `load-01-editor@example.test`). Такой
вход удобен, чтобы посмотреть консоль глазами роли: у `editor` открыт только
контент, разделы оплаты и аналитики отвечают отказом.

## Объём и время прогона

Полный прогон по умолчанию (20 проектов) на dev-машине — **около полутора
минут**:

| Шаг | Время | Объём |
|---|---|---|
| auth | ~15 c | 20 проектов, 100 операторов, 40 000 пользователей, 4000 записей аудита |
| content | ~20 c | 780 категорий, 3000 постов, 600 медиа, 6000 переводов |
| pay + licensing | ~30 c | 400 000 платежей, 360 000 транзакций, 6000 подписок, 1000 лицензий |
| analytics | ~15 c | 2 000 000 событий ClickHouse |

Занятое место — **0.6–0.9 ГБ**: `pay_service` 270–390 МБ, ClickHouse
285–360 МБ, `auth_service` ~30 МБ, `content_service` ~30 МБ, MinIO ~8 МБ.
Разброс — от числа прогонов подряд: мёртвые строки Postgres и старые куски
ClickHouse убираются не сразу. Держите свободными **не меньше 2 ГБ**.

## Повторный запуск и возврат к чистому состоянию

Сидер владеет только проектами с ключом `load-NN` и связанными с ними записями:
перед посевом он удаляет их во всех четырёх сервисах и создаёт заново. Проект
`demo`, проекты, заведённые вручную, и их данные не затрагиваются — ручная
очистка между прогонами не нужна, два прогона подряд дают одинаковые объёмы.

`./tools/cms seed-load 0` выполняет только удаление — это и есть возврат стенда
к состоянию до сидера, включая файлы в MinIO и мутации `DELETE` в ClickHouse
(таблица `events` и все материализованные представления).

## Шаги, которые пока пропускаются

Часть данных опирается на ещё не реализованные разделы платформы. Сидер
проверяет наличие опоры и, если её нет, пропускает шаг, называя причину в
сводке; прогон при этом завершается успешно.

- **Кастомные роли проекта** — нужен каталог прав из изменения
  `access-roles-and-permissions`. Участники пока распределяются по системным
  ролям (`owner`, `admin`, `editor`, `analyst`, `viewer`).
- **Города проекта с SEO** — нужен справочник городов из изменения
  `content-cities-and-regions`.

## Устройство

По одной сеялке на сервис — `apps/<service>/database/seeders/LoadSeeder.php`;
оркестрация — подкоманда `tools/cms seed-load`. Источник истины по составу
проектов — auth-сеялка: она печатает строку `LOAD_PROJECT_IDS` (свои прежние и
новые проекты), оркестратор передаёт её остальным сеялкам вместе с
`LOAD_PROJECTS` — сколько первых проектов из списка засеять. Поэтому сеялки
можно вызвать и напрямую:

```bash
./tools/cms artisan auth-service db:seed --class="Database\Seeders\LoadSeeder" --force
```

Объёмные таблицы наполняются батч-вставками в обход моделей, события уходят
прямо в ClickHouse пачками по 50 тыс. строк. Генерация детерминированная:
зерно выводится из ключа проекта.

В production сидер не работает: каждая сеялка отказывается выполняться при
`APP_ENV=production` до любых изменений данных, а `tools/cms seed-load` не
запускается, если auth-сервис поднят в production-окружении.
